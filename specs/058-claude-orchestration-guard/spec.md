# SPEC-058: Opt-in enforcement policy compiler and guard for parallel Claude Code agents

**Milestone:** M4.6 — Claude Code dynamic workflows

**Status:** draft specification. This is an engineering specification that depends on a preregistered evidence gate it does not own (gate G1, arms A3a and A3b, owned by SPEC-057). SPEC-058 must be implemented as an unreleased engineering candidate (behind the G1 gate) before arm A3 can run; adoption or release happens only after G1 gate GG passes and the ADR is adopted. The candidate is the source tree at a recorded commit that the G1 manifest hashes; it is not packaged, listed or published and is installed by the founder as an explicit local opt-in. Candidate work starts only after the SPEC-057 policy-profile schema increment (SPEC-057 I-3) has merged and the founder has recorded a review disposition of the feature-local ADR proposal ([adr-proposal.md](adr-proposal.md); decided 2026-10-24: review now, adopt with the G1 outcome). Package build, listing, release and adoption are blocked by G1 (a recorded gate GG outcome of pass, with GA pass, and a recorded S2 decision) and by adoption of the ADR. Nothing is implemented, frozen, signed, run, installed or approved. Obtained evidence: none; human review pending.

## Purpose and scope

SPEC-057 gives an orchestrator of parallel Claude Code agents advice: a declared ownership envelope, a pre-flight, receipts at quiescent checkpoints and pull notices (the Mailbox). Advice is communication. Article 12 says prompts, planning and communication reduce risk but do not replace concurrency control when correctness depends on shared state, and the host documentation read on 2026-10-24 states the isolation guidance for agent teams as prose (each teammate owns a different set of files). SPEC-058 specifies the only mechanism-class element of the orchestration family: an opt-in way to turn the same declared ownership into a host-enforced or hook-enforced restriction on what a unit may write, with a published coverage boundary, a ladder of modes that starts at observation, and a liveness attestation that defaults to "advisory only".

The deliverable is a **policy compiler** and a **guard**. The compiler turns declared ownership (the SPEC-057 declaration and the SPEC-057 policy-profile schema) into one enforcement profile with three supported outputs: (D) native host settings, `permissions.deny` plus a sandbox write allowlist (the allowlist semantics are unconfirmed until probe GP-5); (A) a companion plugin with the working name `agent-braid-guard` (a separate package from the notification and ledger companion that SPEC-059 may specify) with `PreToolUse` hooks on Write and Edit and a `TaskCreated` hook; (B) an exported settings snippet for manual paste. The guard is the hook logic of output A. The same `PreToolUse` hook is also the Whisper of the default notification strategy Mailbox + Whisper: it can add a bounded, escaped `additionalContext` to the affected agent in its own session (REQ-012). Output (C), hooks inside the main Agent Braid plugin, is **rejected** and is not representable in any schema of this family.

The guard is not a grant system, a scheduler or a launcher. It never returns `allow`, never holds a grant, never launches, messages as, resumes or authorizes a session, agent or team, and the main plugin keeps its "no installation or session hooks" property. Whether the guard reduces integration failures is a hypothesis (H-OR3, under H-CW2 part (c)) that SPEC-057's gate G1 tests; this specification claims nothing about the result.

## Operation

1. **Declare** (SPEC-057). The orchestrator writes the ownership declaration; the SPEC-057 expansion produces exact paths and a coverage statement.
2. **Compile.** The operator runs the compiler (planned CLI `compile-policy`; name provisional) with the declaration, the unit and a requested mode. It writes, to explicit new private paths, a policy profile and the requested outputs. With no requested mode and enforcement enabled it writes `audit`; with no `mode` member the profile is off.
3. **Apply by the operator.** The operator installs the companion plugin (output A), or supplies the settings document through the host's own mechanism (output D, for example `--settings` in the operator's launcher), or pastes the snippet (output B). Agent Braid performs none of these.
4. **Run.** In `audit` the guard records `would have blocked` and changes nothing. In `warn` it adds context for the agent. In `block` it denies writes outside the envelope and writes to the control paths. In `warn` and `block`, with the default strategy Mailbox + Whisper, the guard may also add a bounded, escaped context for a valid pending pull notice addressed to the agent's unit (the Whisper; recorded as `would-warn` in `audit`). A liveness canary and counters record whether the guard was actually consulted.
5. **Correlate.** At a SPEC-057 quiescent checkpoint, the audit record and the receipt are compared (planned CLI `report-guard`): writes outside the envelope that no guard decision explains are bypass observations; expected-versus-observed guard events give liveness. A refusal of the report (busy, unstable, unobservable, over-bound or malformed input, existing output path) is an error with a stable code and no report.
6. **Revoke.** Uninstall the plugin, remove the settings, set the mode to `off`, or delete the profile. The main plugin is unaffected.

The mode ladder is a progression the operator walks; moving from `audit` to `block` is never automatic and, for release, requires the G1 outcome described under REQ-016. The unreleased candidate may be run in any mode by the founder for the G1 arms (`audit` for A3a, `block` for A3b) because the founder installs and configures it as the operator; that is an experiment configuration and not a release.

## Known limits of the evidence

- A hook that cannot see Bash writes, shell redirects, interpreter writes, MCP-tool effects or generated files provides **no** control over them. Output D can cover them only where HV-8 records it, and only for the paths that deny rules or the sandbox allowlist express.
- The semantics of the sandbox write allowlist are unconfirmed: it may be additive to the default working-directory write access, in which case listing the envelope restricts nothing. Until a GP-5 or HV-8 receipt says otherwise, no restriction is claimed from it.
- The guard cannot attribute writes on a shared tree to a unit without `agent_id`. Unattributed writers (orchestrator, human and shared-tree edits) are `unknown` by default (Article 13), are `not covered`, and are never blocked or blamed as a unit; only an explicit declared exemption rule from the SPEC-057 declaration excludes a path from the report.
- Hooks fail open: a crash, timeout, malformed output or a non-blocking exit status lets the call proceed; hooks can be disabled by the user or by managed settings. Liveness is therefore an observed property per surface and version, never an assumption.
- A controlled agent can attempt to edit its own envelope, settings or hook scripts, including through Bash. Control-path protection is bounded by the same coverage boundary and measured by G1 (criterion CG1, tamper).
- Conservative ownership costs parallelism and produces false blocks. One single-author preprint reports that a pre-write admission mechanism failed closed in 46 of 90 runs on undeclared scope, with a different mechanism and small n; it is a warning that fail-closed has costs, not a predicted rate. Another reports that most freshness-based blocks are benign. Neither measures Claude Code.
- Escaping does not neutralise semantic prompt injection. Closed templates and SPEC-057's escaping keep repository text out of instruction positions and remove control and bidirectional characters, which proves template integrity and nothing about what a model does with a data field that reads like an instruction. The cross-unit route is the concrete case: a unit can create a file whose name addresses another agent, and any path that a rendering forwards would carry that name into the other agent's context. This specification bounds the Whisper route by construction (the Whisper forwards no sibling-written path text; REQ-012) and states the rest as a **residual risk**: any other route by which one unit's file name, commit subject or task text reaches another agent (tool results, directory listings, task text the host shows) is not controlled by the guard, and G1 does not measure it.
- G1's guard arms are compared with hand-written native controls only if the optional arm `AN` runs. Unless it ran on the claimed surface, a GG pass shows that the candidate met its criteria and nothing about value over `permissions.deny` and sandbox settings written by hand from the same declaration; the release wording must say so (REQ-016).
- The dogfood datum (three fan-outs, one stale-read event, no outcome measured) is an anecdote. No prevention claim follows from it, and demand for blocking is not evidenced; blocking through hooks is parity with existing tools (research.md).
- Hosts change weekly and several surfaces are experimental or research previews. Every statement about a surface is tied to a host version and is not a claim about later versions.

### REQ-001 — Compile declared ownership to a policy profile deterministically

**SC-001:** Given a SPEC-057 ownership declaration, a unit id, a requested mode and the set of requested outputs, when the policy compiler (planned `agent_braid/guard_policy.py`) runs, then it emits a profile that validates against SPEC-057's `policy-profile.schema.json`; the envelope is derived from the SPEC-057 expansion (exact repository-relative paths and create regions) and path identity and the prefix-overlap rule are reused from that module and not spelled a second time; the output is byte-identical for identical input; an envelope with any entry that did not expand exactly is marked partial, is compiled in `audit` or `warn` with the partial entries listed as undecidable, and is refused in `block` unless the operator supplies a stricter explicit exemption record; the compiler refuses a unit absent from the declaration, a declaration over the SPEC-057 bounds, a request for output C or any target inside the main plugin, and any member that would carry an `allow`, a grant or content, each refusal being an error with a code from SPEC-057's `command-error.schema.json` (`ERR-OVER-BOUND` for a declaration over the bounds, `ERR-MALFORMED-INPUT` with a rule from the command's closed list for the other cases, `ERR-OUTPUT-EXISTS` for an existing path; the mapping is in `contracts/README.md`), a nonzero exit and no profile (a refusal is never a result, while a partial envelope in `audit` or `warn` is a result listed as undecidable and not a refusal); the profile's `coverageBoundary.tools` names Write and Edit (NotebookEdit only if the founder accepts the proposed extension), `enforcementObserved` is false and `attestation` is absent; `failureBehavior` is present whenever a mode is enabled; `executionAuthorization` is false; the rules that JSON Schema cannot express are compiler and validator rules tested here and not implied by schema validation (the `audit` default when enforcement is enabled without a mode, that no mode skips the ladder, that `bash` is `covered-where-verified` only for the native-settings output alone with an HV-8 attestation, the partial-envelope refusal in `block`, and that the recorded envelope digest matches the envelope); and the compiler writes only to explicit new private paths, refuses existing paths and never touches a settings file.

Failure and inconclusive cases: a nondeterministic output, a profile that validates with an `allow` or a grant, a partial envelope compiled in `block` without the exemption record, a second implementation of path normalization or overlap, an overwritten path, a refusal that appears as a result, a rule listed above as a compiler rule that only schema validation checks, or an edit of any settings file fails the requirement. A SPEC-057 module or schema that does not yet exist is an unavailable observation, not a pass.

Verification: [procedure_req_001](validation-plan.md#procedure_req_001). Planned evidence only; obtained evidence: none.

### REQ-002 — Compile output D: native permissions and sandbox write allowlist

**SC-002:** Given a profile and the other units' declared paths, when output D is generated, then the document contains a `permissions.deny` list and a `sandbox.filesystem` write allowlist in the host's documented settings shape (documentation reading of 2026-10-24; syntax re-verified against the then-current documentation before release); because ownership is an allowlist and `permissions.deny` is a denylist (deny wins over allow), the deny list enumerates the other units' declared write and create paths and the protected control paths and never claims to deny "everything else"; the sandbox write allowlist lists the unit's own envelope and is labelled in the document, the matrix and every report as **unconfirmed: whether it restricts subprocess writes or is additive to the default working-directory write access, and how it relates to default working-directory writes (HV-8, GP-5)**, so that no OS-level bound and no restriction is stated until a receipt records it; the document states that both lists are host configuration supplied by the operator and are not Agent Braid authority and not a grant; a path that cannot be expressed exactly is listed as `unexpressible` and lowers the stated coverage; the output carries the coverage boundary with `bash` equal to `covered-where-verified` only when an HV-8 receipt for that surface and host version is bound and records that the allowlist restricts, otherwise `not-covered`; the output states that it applies only where the operator supplies it and that on a shared tree it is not per teammate; and the output is not offered for a surface where HV-8 is a fail or unobserved.

Failure and inconclusive cases: a deny list that contradicts its own allowlist, Bash coverage claimed without a receipt, an OS-level bound or a restriction claimed from the allowlist without a receipt, an allowlist described as a grant or as Agent Braid authority, an inexpressible path silently dropped, an output offered for a surface whose HV-8 is a fail, or wording that says the output enforces or prevents fails the requirement. Settings syntax that cannot be checked against the then-current documentation is an unavailable observation.

Verification: [procedure_req_002](validation-plan.md#procedure_req_002). Planned evidence only; obtained evidence: none.

### REQ-003 — Compile output B: a paste-ready settings snippet that is never applied

**SC-003:** Given a profile, when output B is rendered, then the result is text for the operator to paste by hand, with a header that names the unit, the host version read, the mode, the coverage boundary, the date and the statement that Agent Braid has not applied it; it contains exactly the content of the selected target (output D settings or output A plugin configuration) and no member beyond the profile; it contains no secrets, environment values or absolute home paths beyond the declared envelope; the renderer writes only to an explicit new private path or standard output and never reads or edits any user, project, local or managed settings file; and rendering is deterministic.

Failure and inconclusive cases: any write to a settings file, a snippet that differs from its source output, a snippet without the coverage header, or content from the environment fails the requirement.

## Scientific boundaries and compatibility

Claim separation. *Analogy*: none relied upon (clause zero; Article 18). *Hypotheses* (not requirements; no observation exists): H-OR3, the guard, if later released, has an acceptable false-block and bypass rate on the surfaces where hooks fire, with no successful tamper and observed liveness (G1 gate GG, criteria CG0 to CG5; research hypothesis H-CW2 part (c)); H-GD1, host-native permission deny rules and the sandbox write allowlist cover shell writes that hooks cannot, on the surfaces where they apply to subagents and teammates (HV-8, GP-5; disproof: they do not apply, the allowlist is additive to default working-directory writes and restricts nothing, or they do not stop `sed -i` and redirects outside the allowlist); H-GD2, a Write/Edit guard in `audit` mode records would-have-blocked decisions with a false-positive rate low enough to inform the choice of `block` (disproof: adjudicated false decisions exceed the G1 criterion). Each has its disproof condition in the G1 proposal or in the probe it names. *Empirical*: nothing obtained. *Formal*: no new result; the decision table is a finite check over the conformance vectors (exhaustive-finite over that table only). A null result, a failing GG, a host that cannot support a capability and an inconclusive G1 are valid outcomes, and completing this protocol does not require any hypothesis to be true.

Domain. Claude Code on the local machine; four documented parallel surfaces (`workflow-tracks`, `linked-sessions`, `agent-teams`, `batch`); Git repositories; file-level write targets named by Write and Edit calls (NotebookEdit only if the founder accepts the proposed extension); at most 32 units; the outputs that a recorded probe supports. Not covered: Codex, cloud and remote sessions, the VS Code extension, other hosts, non-Git workspaces, Bash and MCP effects through hooks, unattributed writers, and semantic prompt injection through repository text on any route other than the bounded Whisper.

Observation contract. The operator-owned profile and envelope; the operator-owned settings and notice locations; hook inputs as delivered by the host (path, tool name, agent identity, working directory), reduced immediately to escaped bounded paths and digests; guard counters; SPEC-057 receipts at committed or quiesced snapshots; host behavior only through recorded probe receipts with the Claude Code version. Absent, unreadable, unstable or over-bound observations are unknown or advisory and never mean protected or clean.

Execution contract. The compiler and report are read-only, local, offline and bounded and write only to explicit new private paths. The guard's only effects are a structured host decision and its private audit record. No model invocation, grant, launch, message, resume, merge, network or socket operation; `executionAuthorization` is false in every emitted object; the main plugin's MCP tool set is unchanged.

Compatibility. Additive and gated. No change to `agent_braid/analysis.py`, AIM `0.2.0-draft`, the SPEC-052 gate, SPEC-057's schemas and commands, the plugin MCP tools, limits or grants, the existing five product skills or the main plugin package. The companion plugin, the compiler module and two CLI subcommands are the only additions. They exist first as an unreleased engineering candidate (behind the G1 gate) and become a packaged, listed or released artifact only after G1 gate GG passes and the ADR is adopted. The next plugin release number is the founder's decision and is not implied. The SPEC-057 policy-profile schema is consumed unchanged; if it must change, that is a SPEC-057 amendment.

### Planning interpretations by the drafting track (proposed; not founder-approved)

These choices fill gaps the decisions leave open. They are listed so the founder can accept, amend or reject them; none is recorded as approved.

- **D versus B:** output D is a per-unit settings document that the operator's own launcher or settings placement supplies through a host mechanism; output B is the same content rendered as paste-ready text for the operator's own settings files. Both are produced by the compiler and applied only by the operator.
- **Inversion:** because `permissions.deny` is a denylist and deny wins over allow, output D denies the other units' declared paths and the control paths; the sandbox write allowlist lists the unit's envelope, and whether that restricts subprocess writes is unconfirmed (GP-5).
- **Mode semantics:** `warn` is `additionalContext` only (the agent sees the advisory and the call proceeds); `block` is `deny` for outside-envelope and control-path writes and `ask` for undecidable paths. `ask` behavior inside non-interactive subagents is unverified (GP-2).
- **Profile mode versus settings mode:** the compiled profile `mode` is the lowest-precedence default beneath the user scope; the scope-resolved `guardMode` of the SPEC-057 resolver (with the block floor) overrides it, and the guard reports the source. The decisions fix precedence among scopes only; the alternative (the stricter of the two) would stop an operator from setting `off` at a scope without deleting the profile.
- **Whisper delivery:** the Whisper is delivered by the same `PreToolUse` hook in `warn` and `block`, from a validated pull notice in an operator-owned location, at most once per notice and agent; it fires only when the agent calls a matched tool.
- **Candidate versus package:** the unreleased candidate is the companion source tree at a recorded commit loaded by the founder as a local opt-in; only a package build, listing or release passes the REQ-016 gate.
- **Per-surface gate outcome:** the release decision records an outcome per claimed surface and output, and only surfaces with a `pass` are claimed, which reconciles "at least one" (the gate) with "each claimed surface" (the release).
- **Partial envelopes:** `block` is refused for a partial envelope without an explicit operator exemption record; `audit` and `warn` are allowed.
- **Task footprint marker:** the `TaskCreated` check reads only a structured marker line and never natural language.
- **Coverage tools:** the founder decision names Write and Edit. NotebookEdit is a proposed extension of the coverage boundary (the SPEC-057 schema represents it only as pending acceptance); until the founder accepts it, profiles, matcher and matrix name Write and Edit only.
- **Whisper path policy:** because escaping does not neutralise semantic prompt injection and the Whisper would otherwise forward a sibling-written file name into another agent's context, the Whisper carries unit ids, hazard kinds, a path count, path digests and at most 4 paths that equal the receiving unit's own declared paths, and no sibling-written path text. Proposed, not founder-approved; the founder may widen it, at the cost of the residual risk stated in the Known limits.
- **Refusal mapping:** the compiler, the report and the package builder map their refusals to SPEC-057's closed codes as in `contracts/README.md` (`ERR-MALFORMED-INPUT` with a rule for the cases that code list has no code for). The rule vocabularies are provisional.
- **Companion packaging:** the companion vendors a pinned, hash-checked copy of the pure ownership module rather than importing the main plugin, so the two packages stay independent.
