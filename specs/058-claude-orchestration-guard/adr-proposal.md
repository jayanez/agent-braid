# ADR proposal: Opt-in companion plugin and policy compiler outputs for orchestration enforcement

- **Status:** proposed; not adopted. Drafted 2026-10-24 for milestone M4.6 after the founder's decisions of that date, as a feature-local proposal. Decided 2026-10-24: the proposal is reviewed now and adopted, amended or rejected with the G1 outcome (not before). Adoption is a founder act.
- **Decider:** Juan Antonio Yáñez García, for any future adoption.
- **Amends (if adopted):** [ADR 0024 native AI plugins](../../docs/adr/0024-native-ai-plugins.md), together with the scope that [the SPEC-052 proposal](../052-claude-workflow-gate/adr-proposal.md) discusses for a `workflows/` component. It reopens, explicitly and for the guard companion plugin only, items of that proposal's no-go list (installing or declaring hooks); the SPEC-052 proposal's no-go list carries a cross-note that hooks are reopened only for the SPEC-058 companion, through this separate proposal (an integrator task). It covers the guard companion only: it does not cover the SPEC-059 recorder, monitor, channel or session-socket components of the notification and ledger companion, which need their own ADR and package inventory, nor the reframing of "never messages as a session" that the Doorbell would need.
- **Constitutional articles:** 0, 5, 6, 12, 13, 14, 15, 19, 20, 24. Also ADR 0021 (grant issuance is never model-callable; host approval is not runtime authority).
- **Canonical identity:** none. No ADR number is reserved; the canonical `docs/adr` file is created only at founder adoption (precedent: the SPEC-048 and SPEC-052 proposals). The number is the next free one at adoption and is not predicted here (a parallel branch already carries ADR 0030).

## Context

ADR 0024 defines the native plugin as portable and Claude manifests, the unchanged five product skills, a setup skill, a pinned runtime and the plugin MCP, and states that no installation or session hooks or provider prompts ship. The package tests assert that the main plugin's inventory has no hooks, mods, agents or monitors. The advisory core of the orchestration family (SPEC-057) is read-only and ships no hook. Advice is communication; Article 12 says communication does not substitute for concurrency control where correctness depends on shared state. The founder decided on 2026-10-24 that an opt-in enforcement element may exist, provided that the main plugin keeps its no-hooks property, hooks inside the main plugin are rejected, the guard never says allow and never holds grants, and a preregistered experiment (G1, owned by SPEC-057) precedes any release. Because G1 arm A3 cannot run without the code it gates, SPEC-058 must be implemented as an unreleased engineering candidate (behind the G1 gate) before arm A3 can run; adoption or release happens only after G1 gate GG passes and the ADR is adopted. The candidate is a source tree at a recorded commit that the founder loads as an explicit local opt-in; it is not packaged, listed or published. SPEC-058 specifies the policy compiler and the guard; this proposal records the architectural decision they need.

## Decision proposal

Allow the Agent Braid project to produce and distribute, outside the main plugin package, a **separate companion plugin named `agent-braid-guard`**, and to ship a **policy compiler** that renders a SPEC-057 policy profile into three supported outputs:

- **D, native host settings:** a settings document with `permissions.deny` and a sandbox write allowlist, supplied by the operator through the host's own mechanisms. Preferred where host verification (HV-8, GP-5) confirms it applies to subagents and teammates, and because it is the only candidate that could cover shell writes. The semantics of the sandbox write allowlist are unconfirmed (additive to the default working-directory write access, or restrictive; HV-8, GP-5), so no restriction and no operating-system bound is claimed until a receipt exists. Both lists are host configuration supplied by the operator; they are not Agent Braid authority and not a grant (ADR 0021).
- **A, companion plugin hooks:** `PreToolUse` on Write and Edit (NotebookEdit only if the founder accepts that proposed extension), and `TaskCreated`. Installing the companion is the opt-in; uninstalling it is the revocation. The companion is inert unless an operator-owned policy profile resolves for the session. The same `PreToolUse` hook delivers the Whisper (bounded `additionalContext` to the affected agent in its own session) of the default notification strategy Mailbox + Whisper.
- **B, settings snippet:** the same content rendered as text for the operator to paste by hand.
- **C, hooks inside the main plugin: rejected.** It is not representable in the profile schema, the compiler or any package.

The main plugin package is unchanged byte for byte: no hook, mod, monitor, channel, skill, MCP tool or agent definition is added, and its existing inventory assertions remain unchanged and passing.

## Guard contract

1. **Vocabulary.** The guard emits exactly one of `no-opinion`, `ask`, `deny` or `additionalContext`. `allow` is unreachable, as are `defer`, input rewriting (`updatedInput`) and a continue flag; a contract test over the finite conformance table and a static scan enforce this. In-envelope writes are `no-opinion` (a due Whisper is `additionalContext`, never a decision). `TaskCreated` has no `ask` in the host, so for that event the vocabulary is `no-opinion`, `deny` or `additionalContext`. Because the host combines decisions most-restrictive first, the guard can add restriction or context and can never override another hook or the permission system.
2. **No grants.** The guard holds, issues and accepts no grant (ADR 0021). Override or envelope expansion is an operator or orchestrator act performed outside the guarded agent, never a model-callable operation.
3. **Operator-owned envelope.** The policy profile and envelope live in an operator-owned location that a tool call cannot name; they carry a digest checked on each decision.
4. **Control-path protection.** The envelope and profile files, the audit record location, settings files at every scope, the hook scripts and the companion directory are protected control paths. A conformant profile lists them; the guard applies the mode's decision to writes to them regardless of the unit's envelope. The limit is stated: a Write/Edit hook cannot stop a Bash write to a control path; protection against Bash exists only through output D where recorded.
5. **Liveness attestation defaulting to advisory.** `enforcementObserved` is true only with an attestation (host version, surface, canary observed inside a validity window, receipt). Missing, expired, degraded or tamper-suspected states read `advisory`; a surface where hooks cannot be shown to fire reads `guard-not-covered`.
6. **Fail-open handling.** Hooks fail open and can be disabled by the user or an organization. The guard records every internal error or timeout with a closed code, treats it as `no-opinion` (fail-open, recorded; decided 2026-10-24), degrades the attestation to advisory and never converts an error into a decision or a block-everything fallback. `ask` is used only for undecidable paths in `block` until probe GP-2 settles it. Outputs and documents state that hooks fail open.
7. **Bash bypass recorded.** Bash and other out-of-band writes are outside the hook's coverage boundary. They are recorded after the fact by correlating the guard audit record with the SPEC-057 checkpoint receipt (`shell-write`, `unknown-route`, `control-path-write`, `denied-then-reappeared`); unattributed writers are neither bypass nor violation.
8. **Modes.** `off`, `audit` (records "would have blocked"), `warn` (`additionalContext`) and `block` (`deny`, with `ask` for undecidable paths). A profile with no mode is `off`; the default when enforcement is enabled is `audit`; `block` is never a default and is refused for a partial envelope without an explicit operator exemption record. Scopes: conversation, repository and user; decided 2026-10-24: the most specific scope wins, but a `block` set at repository or user scope is a floor that a conversation setting cannot lower; settings are operator-owned; the compiled profile mode is the lowest-precedence default (a drafting interpretation). A guarded agent has no path to change its mode.
9. **Privacy and injection.** The audit record is content-free (escaped bounded paths, digests, decisions, counters), private and outside the repository; model-visible text is built from closed templates with escaped, bounded data fields, using SPEC-057's single escaping definition. Escaping does not neutralise semantic prompt injection, and the cross-unit route is the concrete case: a file name written by one unit and forwarded into another agent's context. The Whisper therefore forwards no sibling-written path text (unit ids, hazard kinds, a path count, path digests and at most 4 of the receiving unit's own declared paths); every other route is a residual risk that this proposal names, does not control and G1 does not measure. Adoption does not remove it.
10. **No model-controlled path arguments.** The hook reads only the operator-owned profile and envelope, calls no CLI, MCP tool or subprocess with a tool-call string, and so cannot be used to read arbitrary worktrees outside the plugin MCP allowlist.
11. **Release gate.** The companion is packaged, listed and released only against a founder-recorded decision binding the frozen G1 proposal, the evaluated candidate commit, a gate GG outcome of `pass` (which requires GA `pass`) with a per-surface and per-output `pass` for each claimed surface and output, the S2 decision, this ADR's identity, typed host receipts for each claimed surface and version, and the commit of the merged SPEC-057 profile schema. A `fail`, `inconclusive` or downgraded G1 releases nothing, and a surface without its own pass is listed `guard-not-covered`, not claimed. Building and running the unreleased candidate for G1 needs no such record.

## Explicit no-go list

The companion plugin and compiler must not: add any component to the main plugin; ship a skill, MCP server, mod, monitor, channel, agent definition or `SessionStart` hook; emit `allow` or `defer`, rewrite tool input, hold or issue a grant, or treat host approval as authority; launch, message as, resume, stop or authorize a session, agent, team or batch; use `agent.spawn` or `tool.call` mods; post to a session socket or push to any session (the Doorbell and the other push strategies belong to SPEC-059 and need their own ADR); read or write a user's settings files from the compiler; reach the network or open a socket; run `claude`, `git` or the Agent Braid CLI or MCP from a hook; accept a model-controlled path; store file content, edit strings, commands, prompts or transcripts; make prevention, safety, tamper-resistance, speed or uniqueness claims; or cover Codex, cloud sessions, Remote Control, other machines or the VS Code extension. Any additional component needs its own specification and an amendment. In particular this proposal does not cover the recorder, monitor, channel or session-socket components that SPEC-059 may need in its separate notification and ledger companion.

## Authority boundaries

Installing the companion, supplying a settings document and pasting a snippet are acts of the operator; Agent Braid performs none of them. Host approval, auto mode and "Always" approvals are host conveniences, not Agent Braid authority (ADR 0021). The compiler and report are read-only and write only to explicit new private paths; every emitted object carries `executionAuthorization: false`. Analysis and execution remain separate products (Article 20); the guard restricts the writes of its own unit and starts nothing. Article 12 is respected because enforcement is computed by script from a validated envelope, not left to prompts, and Article 13 because every output states its class, coverage boundary and attestation state.

## Alternatives considered

1. **Hooks inside the main plugin (option C):** changes the default behavior of every installed user, contradicts ADR 0024 and the package tests, and was rejected by the founder.
2. **A flag or `userConfig` switch inside the main plugin:** a plugin's hook configuration is active on install and the switch would live in a file the guarded agent may reach; it also leaves the no-hooks wording false. Rejected.
3. **Settings snippet only:** lowest authority impact and kept as output B and as the fallback, but unversioned and untested, and it cannot carry a liveness canary.
4. **Native permissions and sandbox only:** the preferred output where verified and the only candidate to cover Bash, but it cannot express an envelope as an allowlist for denial, is per path and not per teammate on a shared tree, and is unverified on subagents and teammates. It is also the comparator that decides whether the compiler and the guard add anything: G1's optional stage 2 arm `AN` (hand-written `permissions.deny` and sandbox write allowlist from the same declaration, no Agent Braid component) compares them descriptively. Unless `AN` ran on the claimed surface, a GG pass shows nothing about value over native controls alone and the release wording must say so; adoption of this proposal does not depend on that comparison, and the founder may decide the question differently with the G1 outcome.
5. **Mods (`agent.spawn`, `tool.call`) as the enforcement route:** can deny agent starts and tool calls, but run in-process with user permissions, can read prompts and secrets and can send messages; a far larger trust expansion. Rejected.
6. **Fail-closed on guard errors:** freezes work and manufactures false blocks. Rejected; errors are recorded and degrade the attestation.
7. **An `allow` decision for in-envelope writes:** can skip the host permission prompt and silently widen authority. Rejected.
8. **A log-only `PostToolUse` observer using `bashEditDiff`:** documented as best-effort and not for enforcement; not adopted now (decided 2026-10-24); for agent teams the question is decided together with the attributed-write ledger after probe HV-L7.
9. **Ship now without G1:** would release a control whose false-block, bypass, tamper and liveness behavior is unmeasured. Rejected by the founder's evidence decision.

## Consequences and adoption steps

Adoption is a separate founder act taken with the G1 outcome and requires: create the canonical `docs/adr` file with the next available number at that time and amend or supersede the ADR 0024 wording through that file for the companion only; re-snapshot every affected current assurance record present at that moment (specs whose authority inventory includes `docs/adr`, which any new ADR file refreshes) in the same commit, with fresh review, and report changed hashes; produce an authority-impact review for the change (as SPEC-048 does); define the companion package's inventory, builder and verification and update the validation-profile rules; reconcile the milestone index and the SPEC-052 proposal's no-go list; obtain independent review. Until then nothing in `docs/adr` changes, no number is reserved, the main plugin ships no hook, and the companion is not built, listed or published. Adoption alone releases nothing: the release gate also requires the G1 outcome, and the unreleased candidate does not wait for adoption.

What remains open and is not decided here: adoption, amendment or rejection of this proposal (with the G1 outcome); `ask` semantics where no person is present (GP-2); the sandbox allowlist semantics (GP-5); NotebookEdit as a coverage extension; whether the optional G1 arm `AN` runs on a claimed surface; the Whisper path policy (a drafting interpretation); the companion's final name, distribution and version number (after G1); and, later and additively, guard telemetry (SPEC-047 and ADR 0025 first; nothing is collected now).
