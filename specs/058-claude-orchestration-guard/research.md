# Research decisions: SPEC-058

Status: draft. This records what was read, how, with what limits, and the design decisions that follow. Findings carry one of three statuses: **confirmed** (read in the source named), **inferred** (a reasonable reading not stated by a source) and **unconfirmed** (not established). Nothing here is a host observation; the host behaviors that matter are the probes HV-6 to HV-8, HV-10 (SPEC-057) and GP-1 to GP-5 (this specification), each launched by the orchestrating session after the founder authorizes it. Nothing here is a speed or prevention claim. Revised on 2026-10-24 for the founder's second round of decisions (recorded in the specification's Clarifications) and for the review findings on the sandbox allowlist, the surface vocabulary and the evidence labels.

## RS-1. Hooks and what they can and cannot do

Status confirmed unless marked; documentation as read on 2026-10-24.

- `PreToolUse` matches tool names including Write, Edit, NotebookEdit, Bash, Agent, Workflow and MCP tools. Input has the tool name, tool input (for Write the absolute `file_path` and `content`; for Edit `file_path`, `old_string`, `new_string`), `tool_use_id` and the common fields including `cwd`, `permission_mode`, `agent_id` and `agent_type`. A decision is `hookSpecificOutput.permissionDecision` of `allow`, `deny`, `ask` or `defer` (defer in non-interactive mode only), or exit status 2 to block, with `additionalContext` for model-visible text. Multiple hooks' decisions are combined most-restrictive first (`deny`, `defer`, `ask`, `allow`) and `additionalContext` from every hook is kept. Managed hooks run before mods.
- Settings, managed and plugin hooks also run inside subagents (documented), so a plugin hook can see a subagent's calls with `agent_id`. Direct documentation that this holds inside workflow agents specifically is absent (inferred).
- Write/Edit matchers read the path; a shell command that writes files (redirects, `cp`, `sed -i`, `git checkout`) is not seen. `bashEditDiff` is a best-effort list that the documentation says is for finding what to review, not enforcing a policy.
- Hook failures and non-blocking exit statuses do not block (fail open). `disableAllHooks` and `allowManagedHooksOnly` can disable plugin hooks. `SessionEnd` has a short timeout. `@`-mentioned files are not seen. Hooks in cloud sessions run only if the plugin reaches the session; Desktop WSL sessions have no plugins.
- In a Desktop worktree session, project configuration is read from the main checkout root and hook commands run there, while the hook input `cwd` is the worktree path: the guard must use the input `cwd` and its operator-owned envelope location, not the project directory variable (documented; HV-10 and GP-3 to observe).
- `TaskCreated` has no matcher; exit status 2 rolls the task creation back and returns the reason as a tool error; it has no `ask`, and `continue:false` is ignored; it fires only in a session that has the task tools (a documented rule). Whether the task tools are present on the model in use is unconfirmed (HV-7), and so is what the host does with an unmarked task.
- Mods (in-process JS/TS) can deny tool calls and agent spawns, observe and send session messages and run processes; they are a much larger trust expansion and were not selected.

## RS-2. Why ownership becomes a denylist plus a sandbox allowlist

Ownership is naturally an allowlist ("this unit may write these paths"). `permissions.deny` is a denylist and deny wins over allow, so "deny everything, allow my envelope" cannot be expressed; the compiler instead denies the other units' declared paths and the control paths, and lists the unit's envelope in the sandbox write allowlist. What that allowlist does is **unconfirmed**: host write allowlists are typically additive to the default working-directory write access, in which case listing the envelope restricts nothing, and the setting can also read as a write grant, which sits uneasily with "never allow, never grants" and ADR 0021. The compiler therefore labels the allowlist as host configuration supplied by the operator, not Agent Braid authority and not a grant, and states no restriction and no operating-system bound until a GP-5 or HV-8 receipt records one. The Bash coverage claim and the restriction claim are both gated on that receipt. On a shared tree (agent teams) rules apply per path, not per teammate, so per-teammate control from output D is `not-offered` until a probe shows per-teammate settings reaching split-pane processes. This is a design reading of the documentation, to be confirmed by GP-5.

## RS-3. Why `allow` is unreachable

A guard that returned `allow` for in-envelope writes would assert a positive permission, which the host can use to skip its own permission prompt. That would turn a path check into an authorization and conflict with ADR 0021 (host approval is not runtime authority; no grants) and AGENTS.md. The guard therefore returns `no-opinion` (exit status 0, no decision) for in-envelope writes and only ever adds restriction or context. `defer` and input rewriting are excluded for the same reason.

## RS-4. Fail open, liveness and the advisory default

A crashed, timed-out or disabled hook lets the call proceed, and the host does not tell the model. A configuration that "contains" a guard therefore proves nothing about enforcement. The attestation records whether a canary was observed on this surface and host version within a validity window; absent that, the state is `advisory`. Fail-closed on internal errors is rejected (decided 2026-10-24: fail-open, recorded): a deny that the agent cannot act on is a false block by construction and freezes work; instead an internal error or timeout is `no-opinion`, a record, and a liveness attestation degraded to advisory, and G1 measures false blocks and liveness (CG0, CG2). `ask` is kept only for undecidable paths in `block` until probe GP-2.

## RS-5. Tamper

An agent that is denied can try to widen its own envelope, edit the settings or the hook scripts, or write them through Bash. The mitigations are partial and stated as such: the envelope and profile are operator-owned and read from a location the tool call cannot name; control-path writes through Write and Edit follow the mode ladder; the digest check detects a changed envelope; output D can cover Bash writes to those paths where HV-8 records it; G1 includes a tamper-invitation negative control and any success fails the gate (CG1).

## RS-6. Cost of blocking

One single-author preprint reports that a dynamic admission mechanism failed closed in 46 of 90 runs on undeclared scope (with 45 on files already declared), a different mechanism on a different harness; another reports that most blocks of freshness races were benign and that blocking them cost safe completions. Neither measures Claude Code. They are the reason `audit` is the default, `block` is never default, partial envelopes refuse `block`, and false-block and parallelism-retained metrics are preregistered in G1.

## RS-7. Market and prior art

Parity: blocking through `PreToolUse` and plain write exclusion exist in other tools and in native Claude Code controls (claude-net, archived; agent-coord, one commit; TeamBus; relayBrain; mcp_agent_mail leases; native permission rules, sandbox and the task hooks). Clash asks rather than denies. The dated pass of 2026-10-24 (`research/radar/2026-10-24-claude-orchestration.json`, RAD-2026-016 to RAD-2026-033, including the 315-plugin official-marketplace sweep; `docs/strategy/ECOSYSTEM.md`; adoption track AT-2026-007) classifies hook-based hard blocking of Write and Edit as parity and plain write exclusion, leases and locks as behind. The guard is therefore not claimed as a differentiator, and "unknown as a first-class result" is not used as a standalone differentiator either (decided 2026-10-24; Radar reports missing evidence). What is bounded as an application: the guard consumes the same declaration, coverage and class vocabulary as the advisory core, states its coverage boundary and liveness on every output, and is evaluated by a preregistered measurement rather than asserted. The only permitted wording is the bounded claim "no surveyed shipped plugin found", with the query set and the date of the radar snapshot; SPEC-057 task T002 repeats or extends the pass before any publication wording and before release. Interoperability is documentation now and import adapters are deferred. Platform erosion is a recorded risk: Anthropic could ship native ownership enforcement.

## RS-8. ADR 0024 and the opt-in mechanism

ADR 0024 says no installation or session hooks ship, and the package tests assert the main plugin's inventory has no hooks, mods, agents or monitors. A plugin's hook configuration is active on install, so "opt-in" cannot be a flag inside the main plugin without changing every installed user's default. A separate companion plugin keeps the main package and its tests untouched, makes installation the opt-in and uninstallation the revocation, and makes the ADR change narrow and reviewable. The feature-local [adr-proposal.md](adr-proposal.md) records the decision for founder adoption. The SPEC-052 ADR proposal's no-go list (hooks, `agent.spawn` mods, fan-out) is reopened explicitly and for the guard companion only, not overridden, and the feature-local proposal does not cover the SPEC-059 recorder, monitor, channel or socket components. Decided 2026-10-24: the proposal is reviewed now and adopted with the G1 outcome.

## RS-9. HAR.3

T005 (per-host hook and plugin adapters with independent Codex and Claude matrices), T006 (ownership, dependencies and tool/effect scopes in delegated roles), T007 (depth and width) and T011 (lifecycle, canary, incident stop, rollback) overlap conceptually. The guard's canary and revocation are a narrow application of the T011 ideas to one opt-in plugin.

## RS-10. G1 constraints that this specification imposes and consumes

G1 arms A3a (audit) and A3b (block) run the unreleased SPEC-058 engineering candidate from a hashed commit, not a throwaway script and not a released product (decided 2026-10-24, the A3 blocker resolution): SPEC-058 must be implemented as an unreleased engineering candidate (behind the G1 gate) before arm A3 can run; adoption or release happens only after G1 gate GG passes and the ADR is adopted. The gate therefore governs release, not implementation. The throwaway log-only scripts remain useful only for the host probes. The product is evaluated through the candidate: its decision table, audit schema and liveness definition are written to match the quantities G1 measures (would-have-blocked records, deny events, bypass and reappearance, canary expected versus observed, hook latency), and T004 checks the consistency. G1 stage 2 also has the optional native-controls-only arm `AN` (a hand-written `permissions.deny` and sandbox write allowlist from the same declaration, no Agent Braid component), compared descriptively with `A3b` and without a threshold; it sets the release wording only, and the release decision records per surface whether it ran. GG is `inconclusive: denominator not reachable at this scale` when the `A3a` projection shows fewer than 20 would-deny events or fewer than 10 tracks with one. A pass of gate GG permits release consideration only and requires a pass of gate GA; a fail closes this specification as not adopted; a downgraded (observational) G1 evaluates no threshold and cannot release the guard.

## RS-11. Minimum viable cut and alternatives

The minimum cut that can be evaluated is output A in `audit` mode on one surface with the decision core and the audit record. Output D is preferred where HV-8 supports it because only it can cover Bash. Output B is a documentation fallback. A log-only `PostToolUse` Bash observer (not now; agent teams are decided with the ledger after probe HV-L7), mods, a ledger-backed guard and automatic mode escalation are deliberately not in the cut.

## Limits of this research

The host documentation was read at the page level on one day and some points rest on a single documentation-index query. No hook, permission rule or sandbox setting was run. The market and literature evidence is thin and mostly secondary; the thresholds restated here belong to an unfrozen proposal. All host-dependent statements are tied to a version and to a probe that has not been run.

## RS-12. Notifications, the Whisper and telemetry

Decided 2026-10-24: the default notification strategy is Mailbox + Whisper. The Mailbox is SPEC-057's pull notice; the Whisper is `PreToolUse` `additionalContext` to the affected agent in its own session, which only a hook can deliver and which therefore belongs to this companion. It is context, not a decision, built from a validated notice with escaped bounded fields (unit ids, hazard kinds, a path count, path digests and at most 4 of the receiving unit's own declared paths, and no sibling-written path text, because escaping does not neutralise semantic prompt injection; a drafting interpretation), delivered at most once per notice and agent, and it fires only when the agent calls a matched tool, so it can be late or absent. The Megaphone (monitor or channels) and the Doorbell (data posted to the orchestrator's own session socket) are opt-in in SPEC-059 and are not part of this package. Telemetry is a narrow-go deferred: nothing now; later only the guard decision mix by mode (including would-have-blocked) and hook duration buckets, after SPEC-047 and ADR 0025 are adopted and the guard has shipped, with a never-collect list that becomes a specification exclusion (REQ-012).
