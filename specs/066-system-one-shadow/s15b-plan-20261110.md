## 1. Facts this plan rests on (verified on develop at c9625960)

1. **Consent scope.** The T101 record admits `dataClass: structural-only`, one
   workspace (`eedc05f71069fdb4af00c6b99932195b`, with registered worktrees), two
   explicitly excluded workspaces, 30-day retention, revocation by
   `system-one purge`, `executionAuthorization: false`, `trainingAdmission: false`.
   Its `sourceFamilies` are: System One shadow episodes; real runs (runtime
   conflict, merge conflict, verify result); SPEC-047 telemetry; SPEC-053
   transcript adapter output; SPEC-059 real-use sources. **Git-history replay is not
   listed** (finding F1, section 9).
2. **Episodes carry no workspace and no run link.** `episodeId` is a random UUID,
   there is no repository field, and the store (`salt.key` plus
   `episodes-<day>.jsonl`) is host-global. Episodes from the two excluded
   workspaces can sit in the same store. The only per-repo trace is
   `resourceHashes`: salted pseudonyms (HMAC with a repo salt derived from the
   store secret and the configured `source_root` string), at most 32 per list,
   `null` when no salt exists.
3. **Pinned files.** These are bound by `current` evidence pins of other specs and
   must not be edited (a hash change would invalidate them): `agent_braid/system_one_shadow.py` (SPEC-074, and the S1.5a
   freeze), `git_replay.py` (052), `git_adapter.py` (052, 057, 058, 059),
   `git_process.py` (065), `tooling_telemetry.py` (059, 074), `cli.py` (067),
   `analysis.py` (052, 053, 057, 058, 059, 069). Private helpers of those modules
   (for example `git_replay._sanitized_environment`) are not imported where avoidable:
   small pieces are copied instead (section 2.4). Consequences: no new `system-one`
   subcommand, no new episode field, no new store file kind inside the shadow
   store, no `merge-tree` helper inside `git_process.py`. Everything below is
   additive and imports those modules read-only. (If an implementer finds that a
   needed change touches a pinned file: STOP and report; never rewrite hashes.)
4. **`git merge-tree` precedent.** `agent_braid/git_integration_prototype.py:290`
   already runs `merge-tree --write-tree` through `run_git` in a scratch repository;
   it treats any nonzero exit as a conflict, which this plan does **not** copy (only
   exit 1 with a parsed tree line is a conflict; other codes are unlabelled). SPEC-012's replay planner
   (`git_replay.produce`) replays patches into an isolated index and records a
   tracked-tree observation; it is not a three-way-merge oracle.
5. **Existing precedent for research tooling:** `research/owned_work_coverage.py`
   (pure, offline, shipped in the `research` package already listed in
   `pyproject.toml`) and `scripts/spec066_t030_receipt.py` (one-command, read-only,
   counts-only evidence JSON). Both are followed here. Python is 3.13
   (`/opt/homebrew/bin/python3.13`); `dependencies = []` is unchanged.

## 2. Task structure, file layout and ordering

### 2.1 Wave W0: the corpus gate (prerequisite, under T101 / REQ-101)

REQ-101 says admission "is restricted to plugin-registered workspaces". The T101
record validates scope digests only; nothing yet *enforces* it on a path. Both T102
and T106 need that enforcement, so it is built once, first, and merged before they
start in parallel. It is not a new task number: it completes the enforcement half of
T101 (the orchestrator may attach it to T101 or to T102).

| New file | Purpose |
|---|---|
| `research/s15b_corpus_gate.py` | `load_consent()`, `admit_path()`, closed refusal codes, source-family check, retention helper |
| `tests/test_spec066_s15b_corpus_gate.py` | positive and negative controls (section 6) |

Behaviour:

- `load_consent(path)` reads the T101 record (bounded, regular file), recomputes the
  three digests with `agent_braid.owned_work_authority.digest`, and requires
  `executionAuthorization` and `trainingAdmission` both `false`, exactly one admitted
  workspace, and both excluded ids. The admitted workspace id is **also a literal
  constant in the module**: a widened or swapped record fails against the constant,
  so changing the corpus needs a code change and review, not only a data edit.
- `admit_path(path)` realpath-resolves the path (no symlink escape, no `..`), loads
  the registry with `plugin_registry.inspect_registry()` (read-only; workspaces are under `['value']['workspaces']`, stale worktree roots already filtered; a quarantined row counts as `workspace-not-registered`), finds the
  workspace whose `workspaceId` equals the admitted constant, and admits the path
  only when it lies inside that workspace's `sourceRoot` or inside one of its
  registered, existing `worktreeRoots`. It refuses a path inside any excluded
  workspace's roots even when also nested under an admitted root. It returns
  `{workspaceId, rootKind}` and never a path in any message or output.
- Refusal codes (closed set, counted, never echoing input): `consent-invalid`,
  `registry-unavailable`, `workspace-not-registered`, `workspace-excluded`,
  `path-outside-admitted`, `source-family-not-admitted`, `retention-expired`.
- `require_source_family(name)` checks `name` against the record's
  `sourceFamilies` (plus an addendum record if one is supplied and digest-bound). It
  is how T106 real runs stay blocked until F1 is resolved.
- `retention_cutoff(today)` returns the first admitted UTC day (today minus 30 days);
  stores purge older records on every write and read, as the shadow store does.

The admitted id literal ships in the `research` package; the consent calls the id
low-sensitivity, so this is accepted. Evidence JSON and logs key counts by closed
names only and never print a workspace id. The orchestrator may instead fold the gate
into T102 (section 3); W0 is recommended only if T106 must start in parallel.

The gate does not mint a SPEC-051 authority descriptor (that needs the T103 and T104
pins and a trusted operator registry; it gates fitting, which S1.5b does not do).

### 2.2 T102: outcome observer (REQ-102)

| New file | Purpose |
|---|---|
| `research/s15b_outcome_observer.py` | read-only episode reader, outcome sources, in-memory matcher, outcome record writer, purge |
| `scripts/spec066_s15b_observe.py` | one command: `--yield-report` (default, writes nothing), `--write` (appends joined records), `--purge`; evidence JSON to `specs/066-system-one-shadow/evidence/s15b-observe-<date>.json` |
| `tests/test_spec066_outcome_observer.py` | tests first |
| `tests/fixtures/spec066_s15b/outcomes/**` | synthetic episodes, salts and outcome sources only |

Inputs: (a) shadow episodes, read through the store's bounded safe-open rules (no
symlink, regular file, 0600, 4 MiB cap) and `validate_episode`; (b) the store secret
read **without creating it** (public `default_directory()` and `SALT_FILE`, then a
bounded private-file read; the shadow module's `_secret()` creates `salt.key` and must
never be called here; the private `_repo_salt` and `_pseudonym` are the only private
names used, pinned by test T102-9). Reading the host-global store touches episodes of
the excluded workspaces; they are used for in-memory matching only, never persisted,
and an unmatched episode leaves no trace; (c)
outcome sources behind one small protocol `OutcomeSource.outcomes(window)` yielding
`(outcomeKind, day, admission, left_resources, right_resources)` where resources stay
in memory only.

Outcome kinds (closed): `runtime-conflict`, `merge-conflict`, `verify-pass`,
`verify-fail`. T102 emits kinds, never labels; T103's rubric maps kinds to labels, so
the two tasks stay parallel.

Sources, in priority order, each admitted only through `admit_path`:

1. **Pair-level real-run sources** (local run directories and reports of the
   runtime and verify paths under the runtime state and plugin result roots listed in
   `REAL_USE_EVIDENCE.md`). **Unverified assumption A1:** that these retain per-pair
   resource sets. **Expected result: zero** (SPEC-047, 053 and 059 are aggregate; no runtime report is
known to hold resource sets). Step 0 of T102 is therefore a pre-implementation,
read-only structural inventory (counts of
   readable run records by kind and day, no content) written to the evidence JSON
   before any matcher code is trusted. If no source retains pair-level resources, T102 is
descoped to the matcher, record writer and tests on synthetic sources (the future fix
is to have a runtime path hand the episode's random id to the outcome, which needs a
change to pinned files and a new decision), and delivers the observer, matcher and tests on synthetic sources, and reports
   yield 0 (valid; the track stays in shadow collection, plan.md).
2. **Aggregate-only sources** (SPEC-047 telemetry, SPEC-053 transcript output,
   SPEC-059 ledger as far as they hold no resources) contribute **yield accounting
   only** (counts of verify and conflict outcomes per day). They never produce a
   label: transcript-derived effects are `partial` coverage by SPEC-053 SC-005 and no
   outcome is inferred from transcript text.

Join: for each outcome with resources, compute the pair's pseudonyms under each
candidate repo salt. The salt is HMAC of the exact `source_root` string the MCP
adapter was configured with, not a realpath, so candidates are the raw registered
`sourceRoot` and worktree strings and their realpaths (and trailing-slash variants);
a worktree string gives a different salt than the source root. Because a string
mismatch looks like honest absence, `no-match` is split into counters `no-episode`
and `salt-unmatched`, and a positive control (T102-11) runs in the evidence and look for a
**unique** episode pair whose `left`, `right` and `shared` hash lists equal the
computed lists (the 32-lowest truncation applies to both sides identically), with
episode day within `[outcome day minus 7, outcome day]`. Exactly one match joins.
Zero matches stays unlabelled (`no-match`); several matches stays unlabelled
(`ambiguous`). Nothing is imputed. An episode pair with `resourceHashes: null` cannot
be attributed to the admitted workspace and is **never** corpus (fail closed): this
is how episodes of the two excluded workspaces are kept out, since the store itself
cannot separate them (fact 2).

Output record `agent-braid-s1-outcome/v0.1` (JSONL, one object per line, canonical,
0600, directory `system-one-s15b/` beside, not inside, the shadow store; bounded
files and counts like the shadow store):

`schemaVersion`, `joinKey` (random UUID4 from `secrets`, never derived from any
input digest), `day` (the **episode** day, so retention counts from the observation,
not from the join), `source` (`real-run`), `outcomeKind`, `joinStatus`
(`joined|no-match|ambiguous`), the matched episode pair's already-structural v0.2
pair object copied verbatim (so the record is self-contained and survives the
episode's own purge), `executionAuthorization: false`. No `episodeId`, no path, no
resource name, no commit or run identifier, no hash input.

Revocation gap (finding F2): the consent names `system-one purge`, which removes only
the shadow store and cannot be extended (pinned module). `--purge` here removes the
S1.5b store, and the guide states both commands. Owner review item.

Acceptance (tasks.md T102 text, "joins DP-1 episodes with a later runtime conflict,
merge conflict or verify result under a random join key; pairs without an outcome
stay unlabelled"): tests T102-1 to T102-9 in section 5.

### 2.3 T103: amended label rubric (REQ-103)

| New file | Purpose |
|---|---|
| `specs/066-system-one-shadow/contracts/label-rubric-v0.1.md` | normative rubric text |
| `specs/066-system-one-shadow/contracts/label-rubric-v0.1.json` | machine-readable frozen rubric (closed vocabulary, mapping, policies, sampling parameters) |
| `research/s15b_label_rubric.py` | loader and validator, `rubric_digest()`, deterministic adjudication-sample selector, noise estimator |
| `tests/test_spec066_label_rubric.py` | tests first, including the pinned digest |

Content of the rubric (frozen *before any fit*; the digest pin is a test constant, so
a later edit fails CI until deliberately re-pinned in a reviewed change):

- **Outcome-to-label mapping** (observed outcomes primary): `runtime-conflict` and
  `merge-conflict` map to `conflict`; `merge-clean` (from T106) maps to `textually-clean` and `verify-pass` (after a
  combined execution) to `no-conflict-observed` (two labels, never pooled by default); `verify-fail` is its
  own `integration-failure` label and is **not** collapsed into `conflict` (a failed
  verify does not prove the pair conflicted). The oracle for T106 is `merge-tree`;
  for T102 it is the observed run result.
- **DP-1 scoring vocabulary:** which labels count as truth for
  `likely-independent` / `likely-conflicting` / `undetermined`; `undetermined` is
  never scored as right or wrong, only counted.
- **Missing-label policy (frozen):** unlabelled pairs are never imputed and never
  silently dropped; they are counted by class, source and reason; excluded from fit
  and evaluation; every metric reports the unlabelled share and a worst-case bound
  with all unlabelled counted as each label.
- **Adjudication sample protocol:** a stratified random sample (by label and source)
  of fixed size rule `min(40, ceil(0.2 * labelled))` per source, drawn by a PRNG
  seeded from the sealed corpus manifest digest (T104), so the draw cannot be tuned
  after labels are seen. The noise estimand is the owner-vs-observed disagreement
  rate with a Wilson 95 percent interval; with the expected small N the interval is
  wide and is reported as such. No accuracy wording; reported as a limitation of the
  one-person population (spec REQ-103).
- **Adjudication packet fields** (consumed by T105): structural only. See open
  question Q3 (a structural packet may not be adjudicable).
- **Output pins:** `rubric_digest()` supplies the `oracleContractDigest` input for the
  later SPEC-051 descriptor (T104 supplies the feature allowlist and split protocol
  digests).

T103 reads no corpus and needs no gate; it can start at once. Carries forward
SPEC-029 T002 (#286).

### 2.4 T106: git-history replay labels (REQ-104)

| New file | Purpose |
|---|---|
| `research/s15b_git_history_replay.py` | pair enumeration, `merge-tree` oracle in a scratch context, planner reuse, record writer |
| `scripts/spec066_s15b_replay_labels.py` | one command: `--repository PATH` (must pass the gate), `--dry-run`, `--write`; evidence JSON `evidence/s15b-replay-<date>.json` |
| `tests/test_spec066_git_history_replay.py` | tests first; repositories are built in temporary directories by the test, no committed fixture repository |

Pair policy (fixed before any result is seen): (a) for each merge commit in the
first-parent history, the pair is its two parents with their `merge-base`; (b) tips of
local branches with a common merge-base with the default branch and not yet merged.
Per-repository cap 200 pairs (deterministic order, then a fixed-seed sample when over
the cap); each side must change at most 64 paths (the SPEC-012 `MAX_PATHS`).

Oracle: `git merge-tree --write-tree` on the two commit ids. Exit 0 is
`merge-clean`, exit 1 with a parsed tree line is `merge-conflict` (textual
cleanliness, not semantic independence); octopus merges (more than two parents) are
skipped with `octopus`; any other status, a missing object, a
shallow clone, unrelated histories or an unsupported Git (the command needs Git 2.38
or newer, version checked first) is **unlabelled** with a closed reason
(`oracle-error`, `no-merge-base`, `objects-missing`, `too-many-paths`,
`git-too-old`). Safety: the command runs in an empty scratch bare repository whose
object directory is an alternate for the real repository's objects, with a sanitized environment copied into the T106 module (temporary `HOME`,
`GIT_CONFIG_NOSYSTEM`, null global config, no hooks; not imported from the pinned
private helper, and a test pins its keys), so it writes no object
into the owner's repository and cannot execute a merge driver defined in the repo's
local config. Bounded by `git_process.GitCommandBudget` and `run_git` (read-only
import).

Planner reuse (SPEC-012): each pair is expressed as a two-operation
`git_replay` request over immutable commits. The reused pieces are the request
validation and bounds, `analyze_git_with_provenance` through the planner (which
yields the System 2 report), and then `system_one_shadow.build_episode` to produce
the v0.2 structural pair. The planner's own tracked-tree observation of the two
orders is recorded as `plannerAgrees` (`true|false|unavailable`) and **does not
change the label**: `merge-tree` is the oracle the task names, the two procedures
answer different questions (patch application versus three-way merge), and a
disagreement is data about the proxy, not a reason to drop the pair (open question
Q2).

Output: the same `agent-braid-s1-outcome/v0.1` record with `source:
git-history-replay`, `outcomeKind` in `merge-clean|merge-conflict`, random
`joinKey`, the v0.2 pair object and `plannerAgrees`; unlabelled pairs are written
with `joinStatus` `unlabelled` and the reason (counted, never imputed). No commit id,
path, author, message or ref name is written. `day` is the **run date** (history pairs are older than the 30-day window and would be
purged on write if anchored to commit dates); retention for replay records counts from
the run date. Pairing the parents of existing merge commits selects work the owner
already merged and resolved, so `merge-conflict` is over-represented relative to live
runs; this is a stated limitation and T104 reports by source. Pseudonyms in
`resourceHashes` are kept on purpose (T303 ablation) and share the record's life. The shadow episode store is never written by replay, so replayed pairs
cannot be mistaken for real use.

Gate rules: the repository passes `admit_path` first (an unregistered repository,
smart-notes, kinetiq-core and their worktrees are refused); the **real run** also
needs `require_source_family("git-history-replay")`. That family is absent from the
T101 record today, so until F1 is resolved the script runs only against temporary
repositories built by tests (fixture mode) and refuses the owner's repository with
`source-family-not-admitted`. Salt is read, never created; without a salt the
`resourceHashes` stay `null` (attribution is by construction through the gate).

`git_replay.produce` itself runs Git against the real repository; its read-only
behaviour is tested (H-7), not assumed. **Tick criterion:** T106 is fixture-complete
without the addendum; it must not be ticked as delivered until Q1 is answered and one
real dry run is recorded. Carries SPEC-012 and REQ-003 privacy rules. Dependencies T101 (consent, gate) and
T022 (episode v0.2, done).

## 4. Privacy and redaction boundaries (all three tasks)

- Data class is structural-only: closed vocabularies, counts, depth numbers, class
  counts, per-repo salted pseudonyms (as in v0.2). Never a path, resource name,
  commit id, ref, author, message, prompt, transcript text or file content; never in
  a record, a log line, an exception message, an evidence JSON or a test snapshot.
- Evidence JSON from the scripts holds counts by closed key only, with the same
  `LIMITS` discipline as `spec066_t030_receipt.py`; no workspace paths.
- Every read of a repository or run source goes through `admit_path` first. A
  refusal increments a closed counter and echoes nothing.
- Stores: private directory (0700) and files (0600), no symlinks, bounded size and
  count, 30-day retention anchored to the observation day, purge on write and read,
  `--purge` removes everything. Nothing is written inside any repository.
- No network, no subprocess other than the bounded Git calls of T106, no model call.
- Tests use synthetic roots, synthetic salts and temporary repositories only; no real
  root, registry or store of the owner is read by any test.

## 7. Dependencies and risks

- T102 depends on T101 (consent, gate). T103 depends on T101. T106 depends on T101
  and T022. T104 depends on T102 and T103 (the pins for the later descriptor).
- Counterfactual R-A: if no source retains pair-level resources (A1), T102 yields 0
  labels; the corpus then rests on T106 only, and the real-run and replay
  distributions differ. T104 must report by source and never pool silently.
- R-B: the join relies on `resourceHashes` being present, i.e. a salt existed when the
  episode was written. Episodes before the salt (or without it) are unattributable and
  excluded by design.
- R-C: coupling to private helpers of a pinned module; mitigated by the conformance
  test T102-9, which fails if the module drifts.
- R-D: yield. The T030 receipt shows 142 pairs of which about 27 percent are DP-1
  opportunities, all abstained. With the 30-day retention the rolling pool is small;
  the feasibility gate (plan.md) decides, and the population is not widened after
