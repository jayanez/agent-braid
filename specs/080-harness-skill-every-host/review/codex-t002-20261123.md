## What to check

1. **Read-only boundary.** Can the skill as specified be made to run `prepare`, `recover-inspect`, a launch, grant, promotion or registry write, or a telemetry consent change? Check every CLI command that REQ-003 allowlists in `agent_braid/harness_cli.py`, and report any one that has an effect.
2. **Portable fields.** Do the existing seven skills carry fields beyond `name`, `description`, `compatibility` and `metadata` (OD-2 moves `license` into `metadata`)? Would that move break any packaging or plugin test that reads these fields?
3. **Skill path.** Is the planned path `integrations/agent-braid/plugin/harness/SKILL.md` consistent with how `scripts/build_native_plugin.py` collects skills, and with the OpenCode entry `integrations/agent-braid/plugin/opencode/index.js`? SPEC-085 cites the same path. Report a mismatch.
4. **Host registry (OD-4).** Trace every use of `HOSTS` in `harness_hosts.py`, `harness_components.py` and `harness_lifecycle.py`, including `both_hosts_accepted` and the profile validators. Does the split into an inventory and a gate, with profile `v0.2` and legacy `v0.1` reads, preserve each gate's meaning? List any caller the spec does not name.
5. **OpenCode profile (REQ-007).** Compare what `tooling_install.py` writes for OpenCode today with the plural-key schema the spec cites. Is the REQ-007 observation-first procedure sufficient to avoid writing a config that OpenCode rejects?
6. **Validity check (REQ-008, OD-3, OD-6).** Is the held-out procedure (10 prompts × 3 repetitions per host, ≥ 8/10 valid at the first attempt and 10/10 within one retry, all three hosts) fully specified? Check that it fixes prompt authoring and freezing, the definition of "valid", forbidden-effect prompts and how a skill invocation is observed. Is it free of leakage from the skill text into the prompts?
7. **Telemetry (REQ-009, OD-5).** Is the claim that the CLI counters cannot tell calls made by the skill from manual calls correct? Check whether any requirement relies on such a distinction anyway.
8. **Traceability.** Do REQ, SC and procedure IDs match across `spec.md`, `assurance.json`, `tasks.md` and `validation-plan.md`? Are the dependencies between tasks acyclic?

  report missing code as a defect. Do report requirements that cannot be implemented as

  wrong claims about the current code.

  only with a concrete failure scenario; disagreement with a choice alone is not a finding.
- Nothing you write grants approval or authority, and it is not human review.
- Answer with one JSON object that matches the output schema. Each finding needs a concrete
  scenario (situation → wrong result) and the minimal fix. Use `info` severity for
  confirmations worth recording. If you find nothing actionable, return
  `"verdict": "no-actionable-findings"` with an empty or info-only list.
