# M0 formal closure

## Scope

Establish a reviewable M0 closure record without changing the Constitution,
public AIM or certificate contracts, assurance classes, analyzer/verifier
interfaces, or laboratory algorithms. Closure is founder-approved internal
readiness, not independent external replication or production validation.

## Requirements and acceptance

- **REQ-001 — Exit traceability.** SC-009: Given every M0 exit criterion, when
  the closure matrix is reviewed, then it identifies authority, artifact,
  executable evidence, human gate, limits and deferred work.
- **REQ-002 — Portable representation.** SC-010: Given two workload-origin
  fixtures, when validated as AIM records, then text edit, tool read, external
  write and deploy effects preserve identities, dependencies, versions and
  evidence without executing or authorizing an effect.
- **REQ-003 — Compatible evidence.** SC-011: Given captured pilot evidence, when
  M0 readiness is checked, then Python below 3.12, dirty or unknown commits,
  changed inputs and stale digests are rejected.
- **REQ-004 — Equivalent agent exercise.** SC-012: Given sequential Codex and
  Claude reviews of one candidate commit, when closure is checked, then both
  retain unsupported proof as unverified, separate automated evidence from
  approval, preserve scientific limits and report no material divergence.
- **REQ-005 — Separate decisions.** SC-013: Given a founder review record, when
  closure is checked, then scientific review and milestone closure are separate
  explicit approvals and all referenced evidence is bound by digest.

## Boundaries

The executable checker validates structure, provenance and consistency only. It
cannot authenticate a reviewer, establish scientific truth or grant execution
authorization. Third-party reproduction remains a research-preview gate. M0.5
strategy review and M1 analyzer reproduction remain pending in their own specs.
