## What to check

1. **Emission path versus consent (REQ-005, OD-2).** The owner chose offline derivation by
   an explicit command (no hot-path code). REQ-005 and SC-006 still speak of "a harness
   command runs under each" setting and of an explicit local mode. Is it clear which
   command writes spans, whether any harness command other than the derivation command can
   write them, and how `OTEL_*` variables and a skill invocation are shown to have no
   effect? Report any requirement that only makes sense for live instrumentation.
2. **SPEC-047 boundary (REQ-007, OD-1).** Check against `agent_braid/tooling_telemetry.py`
   and the SPEC-047 data contract: is the claim that the store, batch v4, vocabulary and
   consent stay unchanged consistent with the plan, in particular with the planned
   `telemetry-audit` span section (REQ-010) and with "spans and cells join only by UTC day
   and operation"? Does the mapping of `HARNESS_OPERATIONS` and the outcomes `ok`,
   `refused` and `error` to span attributes rely on anything the store does not record?
   Does the audit, which must "open no socket", read the private span store in a way the
   SPEC-047 audit rules allow?
3. **Converter inputs (REQ-003).** Do `harness_journal.py`, `harness_observation.py` and
   `harness_evaluation.py` records carry what the span model needs: attempt start and end
   times, tool-event times, the candidate hash, a SPEC-049 profile id? Name each required
   attribute that no current record can supply, so that REQ-003's "conformance gap" rule
   and the H1 fixture check (T012) are not surprised by it.
4. **Determinism and deduplication (REQ-003, REQ-006).** Trace and span ids are derived from
   record hashes. Is byte-identical repeat conversion achievable when the mapping or pin
   version changes, and does deduplication on re-export hold across a pin change?
5. **Redaction (REQ-004, OD-4).** Is the allowlist-based serializer enough to keep paths,
   user, host and repository names out of resource attributes, span names, `error.type`
   values and `gen_ai.tool.name`? Is `other` the only value for a tool not on the
   allowlist? Is the mutation control in SC-005 able to fail?
6. **Export (REQ-006, OD-5).** The owner chose loopback only (127.0.0.1 or ::1). REQ-006
   still says "an endpoint the operator names". Is the loopback restriction a testable
   requirement, including names that resolve to loopback, redirects and IPv4-mapped IPv6?
   Is "a retry delivers each span once" observable with the standard-library listener of
   T013?
7. **Outcomes (REQ-008, OD-6).** Do the span outcome classes and `error.type` values map one
   to one onto the SPEC-082 infrastructure-error subclasses and the SPEC-083 outcome
   classes, with `unobserved` for missing outcomes? Can any field read as a score or a
   verdict?
8. **Adoption track (REQ-011, OD-7).** Is the AT-2026-004 entry, its current status and its
   `nextDecision`, consistent with the T003 ADR draft and the T015 decision? Does any task
   update the adoption file before the T015 decision?
9. **Traceability.** Do REQ, SC and procedure IDs match across `spec.md`, `assurance.json`,
   `tasks.md` and `validation-plan.md`? Are the dependencies between tasks acyclic?

Statements about the OpenTelemetry GenAI conventions that can only be checked online are
out of reach for this review. Report such a claim only when the repository itself
contradicts it, and say that it was not verified externally.
