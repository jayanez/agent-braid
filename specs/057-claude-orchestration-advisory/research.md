## RS-1. Host surfaces: what is documented

Status confirmed unless marked; all from the host documentation as read on 2026-10-24.

- **Dynamic workflows.** A script-driven background runtime; isolation is opt-in per agent (`isolation: "worktree"`, inferred as above); without it agents share the session working directory. Agents report to the script, not to each other or the orchestrator turn by turn. No shared task list or lock. Up to 16 concurrent agents by default and 1,000 per run. A run is resumable within the same session; a stalled agent restarts from its prompt (up to five restarts) and files it already changed stay changed. Worktrees branch from the origin default branch unless `worktree.baseRef` is `head`. Workflows can be disabled by the user or an organization.
- **Linked and derived sessions.** Background sessions start in the working directory and, before editing, move into an isolated worktree, with documented exceptions (moved or forked in place, sessions already in a worktree, non-git directories, `bgIsolation: none`, writes outside the working directory). Shell writes such as redirects and `cp` are not tracked by the enforcement check. `claude agents --json` is the documented way to read session state from outside; the files under the jobs directory are explicitly not a stable interface. Agent view is a research preview. Cross-session messaging (same machine, plain text, inbound policy, `notify_when_idle`) is the host's own channel. A Desktop session has the worktree toggle off by default. Deleting a session in agent view removes its worktree including uncommitted work.
- **Agent teams.** Experimental and off by default. No worktree isolation: teammates run in the main session directory, and the documentation's guidance is prose (each teammate owns a different set of files). A shared task list and mailbox files exist; the team configuration directory is removed at session end and in-process teammates are not restored by resume. `TeammateIdle`, `TaskCreated` and `TaskCompleted` can block with exit status 2; `TaskCreated` (changelog 2.1.84) fires only in a session that has the task tools, and the documentation says those are present by default only on some models (a documented rule; presence on the model in use is unconfirmed: HV-7).
- **`/batch`.** A bundled skill that decomposes a change into five to thirty units, presents a plan, and after approval spawns one background subagent per unit in an isolated worktree; each unit publishes its change. How results are merged and the branch layout are not documented (unconfirmed: HV-11). There is no host hook at plan approval.
- **Hooks.** Settings, managed and plugin hooks run inside subagents with `agent_id` and `agent_type` (documented for subagents; inferred for workflow agents and `/batch` units; unobserved for teammates, HV-6); `PreToolUse` can deny, ask or inject context and its decision `allow` can skip the permission prompt; Write/Edit matchers do not see shell writes; `bashEditDiff` is a best-effort list that the documentation says is for finding what to review, not enforcing a policy; hooks can be disabled by the user or an organization; non-blocking exit codes fail open.
- **Notification routes** (only the pull notice is adopted here; hook context is SPEC-058's Whisper; the rest are reserved or excluded, see RS-5): channels (research preview, allowlist-gated), plugin monitors (experimental, interactive only), hook context into the hook's own session, a hook posting to its own session's socket (wire format undocumented), and mods (in-process JS/TS with spawn and submit APIs). A standard MCP server is pull-only.

## RS-2. Why checkpoints run through the CLI

Facts from the repository (confirmed by code reading): the plugin router holds one global lock acquired without blocking, so a second concurrent call is refused as busy; the service caps four active calls, 32 operations, 1 MiB frames and 360 seconds; a worktree source is accepted only if its resolved path exactly equals an operator-registered root, and a registry change requires a reconnect; the Git adapter observes each source twice and refuses if the snapshots differ, requires at least two operations, treats deletions, renames (detection off), binaries, symlinks and submodules as unknown, and leaves read versions empty. Per-session state lives in process memory. It follows that continuous per-call monitoring through the MCP by many agents is not a workable design; a serialized call at a quiescent point is. The operator CLI has no allowlist and no admission lock, which is why it must not be exposed to agents with model-controlled paths. Whether sessions share one plugin MCP process is unconfirmed (HV-13); the design does not depend on the answer.

## RS-3. Declared-only pre-flight and path identity

The analyzer's resource identity is exact string equality and it treats partial coverage and call/emit/unknown effects as unknown. Therefore (a) a directory or pattern must be expanded before analysis or it silently looks disjoint, (b) anything the expansion cannot enumerate exactly must lower coverage rather than be dropped, and (c) the analyzer is reused unchanged. The directory-aware overlap exists only as a private helper in the scheduler; the plan moves it once into a neutral helper imported by both the scheduler and the ownership module, instead of keeping two copies. A case-insensitive default filesystem, Unicode normalization, symlinks, `./` and `..`, absolute versus relative spellings, and two units creating one new path are the failure classes the critical review named; each is a negative control. The class is `declared-only` because nothing verifies a declaration: an S-Bus-style result (one single-author preprint) reports agent self-reports over-claiming shared resources by 32 to 49 percent, and under-claiming reads is the more dangerous error and is unmeasured.

## RS-4. Disjoint declarations are not merge evidence

One preprint (MERGEGYM, 715 pull request pairs) reports 47.3 percent of textual conflicts (on a stratified set, so not a prevalence) despite disjoint authored file sets, attributed to base mismatch, and that exact local replay with `git merge-tree` is cheap. The consequences adopted: the pre-flight states that disjointness is not merge evidence; the isolation and base audit compares `worktree.baseRef`, the local HEAD and the origin default branch; the SPEC-052 gate stays the integration evidence; and the pre-flight false-assurance rate is a G1 metric. A related preprint reports that most freshness-based blocks are benign, so a read/write overlap verdict can be a false positive; the false-block and parallelism-retained metrics measure it.

## RS-5. Notifications: Mailbox + Whisper by default, push reserved

Evidence for what to carry: one preprint reports that a message describing the specific concurrent change recovered most failing runs while generic detection did not, and another that communication reduced naive conflicts but not task success (CooperBench). Both are small and on research harnesses. The notice therefore carries specific, structured hazard data. Founder decision, 2026-10-24: the default strategy is **Mailbox + Whisper**. The Mailbox is the pull notice that the orchestrator reads; the host already wakes the orchestrator at the end of each turn of a linked session, so a pull notice needs no new channel. The Whisper is `PreToolUse` `additionalContext` to the affected agent in its own session, which is a hook and therefore a SPEC-058 companion output. The notice is data because: Agent Braid never messages as a session (AGENTS.md; ADR 0021); hook context reaches only the hook's own session; an epoch, an expiry and a supersede link address staleness, since a notice that arrives after the state it describes has changed must be detectably old. The **Megaphone** (plugin monitors, which are experimental and interactive only, or channels, which are allowlist-gated research previews) and the **Doorbell** (a script posting data to the orchestrator's own session messaging socket; wire format undocumented, so unconfirmed) are opt-in, reserved for SPEC-059, enabled only if G1 shows late notices with measurable harm and, for the Doorbell, a transport verified after G2, and the Doorbell needs an ADR that reframes "never messages as a session". Mods remain excluded (a large trust expansion). A standard MCP server is pull-only. The orchestration-settings schema carries the strategy and a versioned extension point so that SPEC-059 can extend it; nothing here implements push. Late-notice harm is measured by G1 (notification volume and the A2-against-A1 comparison), not assumed.

## RS-6. Control outputs and why the schema is owned here

The founder's decision fixes three outputs (native settings, a companion plugin, an exported snippet) and rejects hooks inside the main plugin. Reasons the record supports: ADR 0024 says no installation or session hooks ship and the package tests assert no hooks, mods, agents or monitors in the inventory; native permissions and the sandbox are host-enforced, are the only candidate that could cover shell writes, and need no hook, but whether they apply inside subagents and teammates is unverified (HV-8); hooks cover Write and Edit only and can be turned off. Tamper and fail-open were raised by the critical review: a controlled agent can edit its own envelope or settings and hook errors allow, so the schema requires protected control paths and an `enforcementObserved` attestation defaulting to false, and the vocabulary has no `allow`. A guard that emits `allow` could skip the host's permission prompt, which would silently widen authority (ADR 0021). The compiler and hooks are SPEC-058; owning the schema here lets SPEC-058 consume it and lets a conformance test fix the invariants before any code exists. Added 2026-10-24: a guard internal error or timeout is fail-open and recorded (no opinion, a record, liveness degraded to advisory), `ask` is kept only for undecidable paths in `block` mode until probe GP-2 settles it, the coverage tools are Write and Edit (NotebookEdit is an extension proposed by SPEC-058 and not accepted), and an enabled mode requires protected control paths. Bash coverage is claimed only with the native-settings output alone and an HV-8 attestation. The audit default and the ladder are compiler and validator rules that JSON Schema cannot express.

## RS-7. Market and prior art

Source: the recorded pass of 2026-10-24 in `research/radar/2026-10-24-claude-orchestration.json` (RAD-2026-016 to RAD-2026-033, query set and limits recorded there), the section of `docs/strategy/ECOSYSTEM.md` that summarizes it, and adoption track AT-2026-007. READMEs were read, nothing was installed and no behavior was reproduced; star counts are point-in-time.

- **Behind or parity, by capability** (radar classification): plain write exclusion, leases, seals and locks (mcp_agent_mail, agent-coord, CoProgrammer, relayBrain, TeamBus, claude-code-merge-queue; claude-net is archived; git-kura is a radar entry known from its README only and is not used here as parity or behind evidence); glob or directory ownership declaration (parity at best); hook-based blocking of Write and Edit (parity; Clash asks rather than denies); textual conflict prediction across live worktrees (Clash, DriftWatch, and Radar for committed branches); symbol-level or contract-level overlap (DriftWatch, Orchestune, TeamBus; Agent Braid resources are exact strings); declared-footprint pre-flight scheduling (OpenWeft, Orchestune: parity, neither known to declare read effects); combined-tree integration checks and merge queues with verification gates (Radar, SVRF, Gas Town Refinery, claude-code-merge-queue, the Mergify plugin); stuck detection and recovery (Gas Town Witness and Deacon, mcp_agent_mail doctor, OpenWeft recovery); messaging, inboxes and notification (mcp_agent_mail, TeamBus and the host's own agent teams and cross-session messaging); durable claim or audit ledgers (Beads, Edda, tracecraft). Syntax-aware textual merge (Mergiraf) is complementary, and fleet launching and management (Gas Town, claude-squad, ccmanager, OpenWeft) is not a goal of Agent Braid. The host itself ships worktree isolation, messaging, task lists, hooks, permission rules and a sandbox. The quick wins (base check, isolation audit, convention list, heartbeat, timestamped notices) are small and easily copied.
- **Reporting uncertainty is not a differentiator by itself.** Radar and other tools report missing evidence, so `unknown` as a first-class result is dropped as a standalone claim (founder decision, 2026-10-24).
- **Bounded candidate.** Only the combination of an Article 13 compatibility class on every output, pairwise classification that includes unknown, declared read/write hazards with explicit coverage, and the declared-versus-observed receipt is retained, and it is itself untested. The literature has read-set validation at write time (STORM, Atomix, S-Bus, MPAC), so any claim concerns application to Git worktrees and Claude Code agent fleets as an advisory, vendor-neutral analyzer. None of this is a moat against a vendor shipping native ownership.
- **Permitted wording.** The single bounded sentence in ECOSYSTEM.md (a dated pass, a recorded query set, "absence within the surveyed set", not a statement about the whole market or about novelty or demand), or `no surveyed shipped plugin found` with the same query set and date. The words unique, only, first, "nobody offers" and any speed term are not used. The pass is repeated before publication wording, before SPEC-058 release and at M4.6 closure (T002).
- **What the pass did not cover** (still open): a peer-reviewed literature query, commercial products (Conductor, Nimbalyst, Sculptor, Devin, Jules, Amp, Cursor, Copilot agent), other plugin directories than the official marketplace snapshot, and any tool that appeared after 2026-10-24. The field is moving: several relevant tools in the pass were absent from the 2026-10-23 radar.

## RS-8. Recovery interfaces

`claude agents --json` is documented as the supported way to read session state; its fields and enumerations are listed in the task text for HV-9 and are documentation readings. Agent Braid takes the output from a file or standard input so that it never launches the host binary. The agent-teams task directory, team configuration and workflow journal are readable on disk but are not documented interfaces; they are best-effort, labelled inferred, and each is dropped if its probe (HV-12) fails. The recovery report uses Git evidence, not an agent's self-report (one preprint reports agents declaring success in most episodes where they had duplicated an effect). It lists information only; reclaiming, resuming or deleting is the user's, and the report warns that agent-view delete discards uncommitted work.

## RS-10. G1 design constraints that this specification imposes

The G1 proposal and its inputs record now exist (drafted by the G1 track, unfrozen) and were read in this revision; the hypothesis entry H-CW2 splits the claim into part (a) advisory arms A1 and A2 (H-OR1 and H-OR2 here), part (b) pull digests of A2 against A1 (H-LD1 in SPEC-059) and part (c) the opt-in guard (H-OR3 in SPEC-058). Constraints from the founder decisions of 2026-10-24: prompt partitioning plus the SPEC-052 gate as baseline (A0); advisory arms A1 and A2; guard arms A3a (audit) and A3b (block); staging, with stage 1 (A0 to A2) first on two surfaces and stage 2 only after the founder reads the stage 1 report; the planned run count and thresholds fixed before the freeze; downgrade to observational findings before launch if EUR 0 is infeasible; the benefit criterion CA1 as an existence screen on designed strata, stated as a limit; gate GG needing at least one claimed surface; the `batch` pre-flight arm decided after the layout probe and before the freeze; metrics of conflicts prevented or caught earlier than the SPEC-052 gate, parallelism retained, false blocks, bypasses, pre-flight false-assurance, declaration recall and precision, enforcement liveness, overhead and notification volume; kill criteria stated in advance; designed-overlap runs reported separately and never used for prevalence; no speed claim. The earlier plan for a throwaway log-only guard arm outside the repository is withdrawn for A3: SPEC-058 must be implemented as an unreleased engineering candidate (behind the G1 gate) before arm A3 can run, and adoption or release happens only after G1 gate GG passes and the ADR is adopted. These are constraints that REQ-013 and the checker pin; the proposal's own text and numbers are the authority.

## RS-11. Minimum viable cut and alternatives

The critical review asked for the cheapest comparator per cell and a minimum variant. The cheapest comparators are host settings (permission rules, worktree isolation), git-kura, Clash, and a ten-line base check. The minimum viable SPEC-057 is therefore: declaration plus expansion plus pre-flight through the existing analyzer, a declared-versus-observed receipt, the isolation and base audit, and the probes, all without hooks, a ledger, a skill or telemetry. Recovery reports, notices, the settings and profile schemas, the matrix and the interoperability contract are smaller additions that make the later specifications possible. If G1 gate GA fails, the specification narrows to the structural parts (declaration schema, isolation and base audit, wording documentation), the orchestration skill stays unbuilt (documentation and CLI help only), and SPEC-058 and SPEC-059 are not adopted; that is a valid outcome.

## RS-12. Settings, skill and telemetry decisions (2026-10-24)

- **Settings.** The most specific scope wins (conversation over repository over user); a `block` set at repository or user scope is a floor a conversation cannot lower; settings are operator-owned and read only from three defined locations (user: the per-user configuration directory; repository: a file outside every working tree, keyed by the repository digest; conversation: a document the operator supplies at invocation), never from a tracked or untracked file inside a working tree. This is stronger than listing the settings files among the protected control paths, which protects nothing in `off` and `audit` modes and nothing against Bash. The locations do not resist a writer with the operator's own file permissions, so the floor is as strong as those permissions and no stronger. The schema carries a versioned `extensions` member so that SPEC-059 completes the push settings under its own schema.
- **Orchestration skill.** Deferred, not discarded. A new or edited skill conflicts with ADR 0024's wording about the unchanged five product skills, so it waits for the ADR amendment and for G1 gate GA (T039). If GA fails, guidance stays repository documentation and CLI help. Guidance ships as documentation and CLI help now.
- **Telemetry.** Narrow-go, deferred: nothing is collected now. A later additive SPEC-047 vocabulary may carry aggregate families A (pre-flight verdict mix), B (guard decision mix by mode, including would-have-blocked) and D (hook and gate duration buckets), only after SPEC-047 and ADR 0025 are adopted and the producing feature ships; family C (host drift canary) only after G1; granularity is no. The never-collect list (paths and hashes; branch, reference and commit identifiers; prompts, messages and transcripts; free text; unit and pair identities; sub-day timestamps; exact durations, token counts and costs; exact model and host builds; per-user bypass and false-block counts; anything from G0 or G1 manifests) is a specification exclusion with planned validator tests (T040, T041).
- **Privacy of host inputs.** The isolation audit reads a closed key list from settings files and persists no other settings value; session `name`, `waitingFor` and `cwd` from `claude agents --json` are used for booleans and counts only. The first draft left this open (settings can hold environment values and tokens; session names and waiting text can carry task text).
- **Probe launch.** The orchestrating Claude session launches the host probes through workflows or derived sessions after the founder authorizes each one; coding agents prepare log-only scripts; the receipt pins the host version.

## Limits of this research

No host observation exists. The literature is preprint-heavy and was not screened for peer review. The market sweep is bounded by the recorded query set and the date. Several host behaviors are unconfirmed and are probes. The dogfood datum is one anecdote. The effect of the advisory on real work, the prevalence of semantic interference in real Claude Code use, and the demand for ownership enforcement are unknown, which is why the value case rests on a preregistered G1 and not on this document.
