## Decisions

### D-1 Commit sources only, refs pinned and re-checked
Decision: accept simple ref names or full commit identifiers; resolve all to 40-hex commits in the validate phase; re-resolve at the end and report moved or deleted references as a stale-ref report with an `inconclusive` overall status. Rationale: the plugin accepts worktree sources only through an operator allowlist and reconnection, which a generic workflow cannot rely on; pinned identifiers make the analysis reproducible and let staleness be detected. Founder clarification: branch or tag names accepted. Alternatives: worktree paths (rejected, allowlist and uncommitted-work ambiguity); commits only (rejected by clarification, branch names are what workflow users hold); silent re-analysis on movement (rejected, hides a changed input). Limit: uncommitted work is never observed and is stated as such.

### D-2 Identifier syntax restricted
Decision: the args schema admits only `[A-Za-z0-9][A-Za-z0-9._/-]*` without `..`, `//`, trailing `/`, `.` or `.lock`. Rationale: prompts then carry no revision expressions, options or raw repository text (REQ-008); a leading character other than alphanumeric cannot become an option. Alternative: allow full revision syntax (rejected, ambiguity and injection surface). Consequence: a user with an unusual ref name resolves it to a commit first; the refusal says so.

### D-3 The validate agent reads the registry through the read-only bootstrap tool
Decision: the validate agent calls `workspaces` once to learn the registered source root and result root for the explicit `workspaceId`, compares the repository root reported by Git, and refuses on mismatch or unknown id; it never selects another workspace. Rationale: the clarification requires refusal when the agent's repository root does not match the explicit workspace; the comparison needs the registered root. The bootstrap tools take no admission lock, so the one-caller discipline of REQ-003 is unaffected. Alternatives: let `analyze-work` refuse (it does, "outside the configured source root", but only after pinning and without a stated rule); call `workspaces` in the analysis agent (delays the refusal past validation). Dependency: HV-1 must show bootstrap tools are visible. The spec text now states this (REQ-002, REQ-003, Operation phase 1) after the 2026-10-23 review.

### D-4 Four agents, strictly sequential, no isolation, no fan-out
Decision: validate, analyze, baseline and finalize are one agent each; report is script code. Rationale: REQ-008 and the plugin lock; four agents also matches the concurrency bound of the MCP. No `parallel()` or `pipeline()` (even over pairs), no `isolation`, no `agentType`, no `workflow()` call, no `model` or `effort` override (founder clarification: inherit session). Alternatives: one agent per pair for the baseline (rejected, fan-out and agent count scale with sources); a single agent for everything (rejected, one prompt would carry decisions the script should own, Article 12). Agent count: none when the arguments are refused, fewer when an earlier phase refuses, is busy or fails, exactly four on every run that completes all four agent phases; finalize always runs in that case because it also re-resolves the references. Limit: agents execute the commands, so a misreport is possible; mitigated by strict schemas, independent re-resolution inside the analyzer, and comparison with direct runs in tests and host receipts; not eliminated.

### D-5 Script-owned decisions
Decision: refusal rules, status, eligibility for replay and prepare, agreement classification, advisory order and limits are computed in script code; agents only return schema-bound observations. Rationale: Article 12. The envelope's `limits` are constants in the script and are required verbatim by the result schema. Alternative: let an agent summarize (rejected, Article 12 and claim discipline).

### D-6 Replay through the MCP `analyze`/`prepare`, not `plan-git`/`verify-git`
Decision: on the MCP path the replay certificate is the evidence and advisory plan produced by the plugin `analyze` tool (which calls the same replay code as `plan-git`) and checked by `prepare`'s independent consumer verification; the CLI commands `plan-git`/`verify-git` are used only on the fallback path. Rationale: verified in code that the MCP exposes no `plan-git`/`verify-git`; `verify` as an MCP tool exists only with runtime mode enabled and is excluded by REQ-005. Alternative: require the CLI for replay (rejected, depends on a constrained Bash permission and would make the primary path weaker). Consequence: the report names the certificate by digests; the spec wording was restated accordingly on 2026-10-23. Limit: when `prepare` is not called, the certificate comes from `analyze` alone and the envelope states that independent verification was not performed.

### D-7 Prepare needs a runtime request the script must derive
Decision: for 2 to 4 operations with complete coverage, no conflicting or unknown pair and a clean baseline, the script builds `order` (a dependency-respecting order; no dependencies are declared, so the instance order), `declaredWrites` (paths from the analyzer provenance, which must equal the observed paths), `uncertainPaths: []` and `expectedFinalTree`. `expectedFinalTree` is derived from the baseline phase by chaining `git merge-tree --write-tree` results in the chosen order with the explicit base as merge base; `prepare` then checks it against its own serial rehearsal and refuses on difference. Rationale: the runtime requires it; deriving it from the baseline avoids a separate write path. Open fact: whether `git merge-tree --write-tree` accepts a tree-ish as a branch argument on the pinned Git is not verified; T005/T011 test it, and if not supported the gate reports `not-prepared` with `expected-tree-unavailable` rather than guessing. Mode is always `serial`; `parallel` is never used (recorded NO-GO results). `runDirectory` is a name under the registered result root obtained from `workspaces`; `prepare` does not allocate it. `advisoryOrder` is `null` unless declared dependencies exist (the gate declares none); the `prepare` order is the input order of `sources`, labelled "input order, not a recommendation" in the schema and the recipe, so it can be read neither as an analysis-supported order nor as order independence. The merge results used for the chain are ephemeral (temporary object directory), never applied. Alternative: skip prepare and only report replay (kept as the degraded outcome).

### D-8 Baseline with a temporary object directory
Decision: `git merge-tree --write-tree --merge-base=<base> <a> <b>` per pair, with a temporary `GIT_OBJECT_DIRECTORY` and the repository store as an alternate, so no object is written to the repository; record refs and `git count-objects -v` before and after. Rationale: founder clarification; `--write-tree` writes tree and blob objects for merge results, which would otherwise create unreachable objects (the repository's portable-root gate rejects unreachable objects, `docs/development/SPEC_KIT.md`). Alternatives: `git merge-tree` legacy trivial merge (rejected, different semantics and deprecated); a scratch clone (rejected, copies the repository and widens disk use); `git merge` in a worktree (rejected, writes state). Git older than 2.38 lacks `--write-tree`: reported as `unavailable`, never clean. The temporary directory is created and removed by the same agent and is outside the repository.

### D-9 File-level agreement is reported, not merged
Decision: report analyzer class and baseline result side by side with an agreement class; the baseline never changes the analyzer verdict and the analyzer never overrides the baseline. A pair where the analyzer says `independent-candidate` and the baseline conflicts is a counterexample that blocks conservativeness wording. Rationale: REQ-006 and REQ-015; H1 is a hypothesis that may be false. `analyzer-stricter` (conflicting versus clean) is expected for same-file different-hunk edits because the analyzer is file-level. Alternative: a combined score (rejected, hides the disagreement the gate exists to show).

### D-10 Packaging as a Claude-only component by default scan
Decision: copy `integrations/agent-braid/plugin/workflows/` to `plugin/workflows/` in `assemble()` behind an explicit pre-adoption opt-in (default: excluded until the ADR 0024 amendment is adopted; the opt-in artifact is engineering-only); no manifest field. Rationale: the plugins reference documents the default `workflows/` scan; existing byte inventory verification already rejects missing, altered or extra files, so the new tests assert rather than extend it. Codex ignores unknown directories (to be asserted by inventory identity of its manifests, not by observing Codex). Alternatives: a `workflows` manifest field (rejected, an unnecessary change to the manifest); copying unconditionally in PR2 (rejected: any package built from `develop` would carry `workflows/` under the same version string as the published alpha.3 bytes, an identity collision, and nothing would stop a build or plugin-dist step from using it); a non-release version suffix for opt-in builds (not chosen: it would touch every version declaration, T038). Package tests assert both the excluded default and the included opt-in; the default flips at adoption (T036). The ADR 0024 amendment is the governance gate (adr-proposal.md).

### D-11 Validation rule for the artifact type
Decision: add an explicit rule in `scripts/validate_change.py`. Verified in code that rules are all-match and `integrations/agent-braid/**` already marks the path sensitive, so the new rule is for clarity and boundary text (host verification, release acceptance) rather than to rescue an unknown path. The adr-proposal consequence text was reworded to say the same: the explicit rule makes the artifact type and boundary text visible, it does not rescue an unknown path. Alternative: rely on `ai-tooling` alone (rejected, the boundary text would not mention the host gate).

### D-12 Testing a plain-JS workflow without the host
Decision: three layers: (a) Node-free structural checks over the source (always run); (b) an optional JavaScript runtime executing the script with mocked globals, runtime version recorded, absence reported as an unavailable observation; (c) real host receipts. Rationale: the runtime is not available offline; the ADR proposal's supply-chain concern argues against vendoring a runtime. A JavaScript runtime is a test-time dependency only, installed in isolated environments, never shipped. Alternative: port the decision logic to Python and test that copy (rejected, the tested code would not be the shipped code).

### D-13 No hooks, mods, plugin agents or `agent.spawn` rewrites
Decision as in the ADR proposal's alternatives 2 and 3. Documented fact: `WorktreeRemove` does not run for workflow-agent worktrees, so hook-based integration is incomplete as well as outside ADR 0024.

### D-14 Claude Code version handling
Decision: the envelope does not claim a host version (the script cannot observe it); versions are bound in host receipts and the recipe. The envelope's `unobserved` list includes `host-version`. Introduced in v2.1.154; documented current v2.1.309 at planning; the behaviors above (resume fix before v2.1.305, workflow permission details) may differ in earlier versions, so supported-version statements wait for T024–T028.

### D-15 Sequencing of PR2 and ADR adoption
Decision (founder clarification): PR2 may merge before adoption provided no version bump, plugin-dist publication or release occurs; R1 requires PR3. Risk: an unreleased executable-looking file sits on `develop` under a not-yet-amended ADR wording; mitigated by labelling it unreleased in the recipe and in the PR and, since the file alone would not stop a build from carrying it under the unchanged version string, by the builder default that excludes `workflows/` until adoption (D-10). ADR numbering: two files share 0024 in `docs/adr` and the highest is 0028, so the number is confirmed at adoption (T034) and none is reserved.

### D-16 One hardened Git template for every phase
Decision: every Git command of every phase uses a fixed template embedded as script constants: `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_TERMINAL_PROMPT=0`, no network, `-c core.hooksPath=/dev/null`, fsmonitor disabled, external merge drivers and content filters disabled; the baseline adds the temporary `GIT_OBJECT_DIRECTORY` of D-8. Rationale: the validate, baseline and finalize agents run `git rev-parse`, `git merge-base`, `git merge-tree --write-tree` (chained for `expectedFinalTree`) and `git count-objects` in the user's repository with the user's configuration; merge-ort can invoke configured merge drivers and `.gitattributes` content comes from agent branches; `docs/architecture/PARALLEL_INTEGRATION.md` keeps credentials, network, hooks, submodules, filters and arbitrary project commands disabled unless a reviewed profile names them. Open fact: the exact overrides that disable every configured driver and filter on the pinned Git are verified with a sentinel fixture (T011) and a native check (T030). A command that cannot be hardened is a stated limit and its phase is unavailable or inconclusive, never run unhardened. Alternatives: rely on the object-store quarantine only (rejected, it does not stop code execution); a scratch clone with a clean configuration (rejected, copies the repository, D-8).

### D-17 Tool surface restricted by registration mode and host allowlist
Decision: the gate refuses (`runtime-enabled-workspace`) when any registered workspace row from `workspaces` has `runtimeEnabled` true or a grant store, and (`unsafe-tool-surface`) when the validate agent reports `execute`, `recover`, `verify` or `status` among its visible plugin tools; the recipe and HV-1/HV-5 require a host permission allowlist (plugin tools `workspaces`, `analyze-work`, `analyze`, `prepare`; fixed read-only Git prefixes) and record the exact tool names and rules. Rationale: with runtime enabled the same plugin MCP exposes model-callable `execute` and `recover`, so a script-computed prompt would be the only barrier (Article 12; ADR 0021, host approval is not runtime authority); the earlier wording treated a bad attempt as a defect to detect afterwards. "Bash constrained to the launcher" (Clarification, CLI fallback) is defined as a session permission rule set allowing the fixed read-only Git prefixes plus the explicit launcher subcommands `analyze-git`, `plan-git`, `verify-git` and the argument-less read-only `plugin workspaces` (registry rules on the fallback, REQ-016(e)) and no rule matching the launcher binary as a whole or its grant and execute subcommands; gate v2 would add only `analyze-claude-transcripts` (planning amendment approved by the founder on 2026-10-24); the documentation says subagents use the session's permission rules, so a per-agent split is not assumed, and Git reads and launcher subcommands coexist for all gate agents. If the host cannot express the rule set, the CLI fallback is no-go and the fact is an input to SPEC-053 REQ-009. Limit: the refusal rule runs after the validate agent, so the allowlist is the only control for that agent; the unsafe-tool-surface check is agent-reported. Alternatives: prompt instructions only (rejected, Article 12); a `Workflow`-level permission only (rejected, it governs the run, not the tools).

## Limits

Fixture agreement is not evidence about real workloads. File-level analysis ignores reads and is coarser than hunk merging. Structural checks, schema validity and profile success are not proof of semantic safety. Negative, null and inconclusive host or corpus outcomes are valid and still allow closure.
