## 1. Facts: `--self-check --founder-go` after #1049 (macOS 27.2, braidlab GUI session by fast user switching, 09:51)

  (`PROC_PIDTBSDINFO`); `launch` ends `self-check-failed` because FS-01 observed `error` (the runs it depends

- Host observation (read-only): the braidlab account has about 347 processes (a full GUI session) and launchd

  `EPERM` for all of them; from braidlab itself it evidently fails for some same-uid processes too.

## 2. Root cause

`_user_processes(uid)` called `proc_pidinfo(PROC_PIDTBSDINFO)` on every pid of the dedicated user, to get the
start time, and `_Lineage.observe` called it again for the parent. `_pidinfo` fails closed on any live process
that is not `ESRCH` or a zombie. The call path that hit `EPERM` is therefore the per-user listing used by
`baseline = _user_processes(uid)`, by the watchdog poll (`_resource_limit`) and by the final sweep, not the
child's group: a process that only exists in the GUI session (not the child, not a descendant) made the whole
run refuse. The sweep also treated every new process of the user as an escape, so even a readable launchd agent
appearing during a run would have killed it and left the run unsettled.

## 3. Change (`agent_braid/harness_containment_macos.py`)

- `_kinfo(pid)`: `sysctl(CTL_KERN, KERN_PROC, KERN_PROC_PID, pid)` into a 648-byte `struct kinfo_proc`; reads
  start time (`p_starttime`), `p_stat`, `e_ppid`, `e_pgid` at fixed offsets (0, 36, 560, 564; offsets checked
  against the real table in a test). No task access is needed. `ESRCH` or an empty answer is "gone"; any other
  errno, a wrong size or a record of another pid fails closed.
- `_user_processes` and `_process_links` (parent and group in one read, discarded when the start time differs)
  use `_kinfo`. `proc_pidinfo` remains only for `PROC_PIDTASKINFO` (resident memory), in `_task_resident`, with
  the same fail-closed rule as before (zombie or gone: 0; live and unreadable: `process-accounting-failed`).
- `_Lineage` classifies a new process as the child's when it is the child, its parent is the child or an
  earlier member, or its process group is led by the child or an earlier member. `members()` is that set;
  `unrelated()` is everything else seen.
- Memory is measured only for the child's own tree; the sweep kills and counts as escaped only that tree.
  Unrelated new processes are neither measured, killed nor counted as escapes.
- Evidence: the run record has `unrelatedProcesses` (distinct unrelated new processes seen) and
  `unreadableProcesses` (those among them that `proc_pidinfo` TASKINFO refuses with `EPERM`, probed once after
  the sweep, never acted on). `scripts/har_t009_attempt.py` prints both, integers only, in `backendRefusals`
  and `probeRuns`. The next self-check shows the noise level and whether the cause above holds.
