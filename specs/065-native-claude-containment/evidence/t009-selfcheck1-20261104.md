## 3. Root cause and the change

Root cause (inferred from the denials, not observed inside the process): the profile granted no
`sysctl-read`, so the Bun runtime could not read its start-up CPU and page-size facts
(`hw.pagesize_compat`, `hw.optional.*`). The `process-exec* /usr/bin/curl` right after those reads is
consistent with a start-up failure path (for example a crash reporter) rather than with a deliberate
download; that reading is a hypothesis. The new exit codes (section 5) will show it.

Founder decision 2026-11-04 (guided question, answer "A. Lista cerrada (Recommended)"): allow a closed list
of read-only system information, nothing else. In `agent_braid/harness_containment_macos.py`, for the
`launch` and `launch-probe` entries only (the `fixture` profile is unchanged):

```
(allow sysctl-read (sysctl-name "hw.pagesize") (sysctl-name "hw.pagesize_compat")
  (sysctl-name "hw.ephemeral_storage") (sysctl-name "kern.osproductversion")
  (sysctl-name "kern.osvariant_status") (sysctl-name "kern.iossupportversion")
  (sysctl-name "security.mac.lockdown_mode_state") (sysctl-name-prefix "hw.optional."))
(allow file-read-data (literal "/usr/share/locale/UTF-8/LC_CTYPE")
  (literal "/usr/share/locale/C.UTF-8/LC_CTYPE") (literal "/usr/share/locale/en_US.UTF-8/LC_CTYPE"))
(allow file-read-metadata (literal "/etc") (literal "/var"))
```

Chosen narrower than "under /usr/share/locale": three literal files, exactly the ones seen. `hw.pagesize`
is on the founder's list although the log shows only `hw.pagesize_compat`.

Still denied (rule absent, covered by tests): `kern.bootargs`, every `mach-lookup`, `/dev/dtracehelper`,
`/System/Volumes/Data` (explicit deny, last rule), `process-exec*` (curl and `/usr/bin/false`), all network
except the loopback proxy port, writes outside candidate, TMPDIR and config_dir.

`__pycache__` write: not allowed. The fixture interpreter now runs with `-B` (compile probe, fixture
spawn) and `PYTHONDONTWRITEBYTECODE=1` in the fixture child environment.

## 4. `process-accounting-failed` for the fixture entry

Raised only in `_pidinfo` (and in `_user_processes` on a failed `proc_listpids`), supervisor side, as
the dedicated user. It is not a consequence of the profile denials: the supervisor is outside the
sandbox. The fixture record shows the compile check passed and the refusal came from `_supervise`, so a
`proc_pidinfo` call failed while `kill(pid, 0)` did not report the process gone.

Realistic cause found by reading the code: a process that exited and is not yet reaped (`SZOMB`) has no
task any more. `PROC_PIDTASKINFO` (used for the resident-size watchdog) fails for it while `kill(pid, 0)`
still succeeds, and the old code treated "alive but unreadable" as a hard accounting failure. The
child tree here is short-lived (preamble python, `sandbox-exec`, the target), so an exiting process in
the list is the normal case on a fast machine. This is a real race, but it is **not proven to be the
failure seen**: nothing native was run for this change. Fix: `_pidinfo` now reads `errno`, treats `ESRCH`
as gone, and when a task flavor fails checks `PROC_PIDTBSDINFO` for `pbi_status == SZOMB` and treats that
as gone too; a live process that cannot be read still fails closed. If the founder's next self-check
still shows `process-accounting-failed`, the new `accountingErrno` and `accountingFlavor` integers in the
refusal record give the cause without the system log.
