### Freeze model (read this before item 7)

The first packet said the snapshots were "historical at this commit". That was wrong for
the candidate's own bytes, and it led to finding C67-001 (rejected in triage). The correct
model is:

- `scripts/validate_spec_kit.py freeze` needs a clean candidate. It takes `HEAD` as the
  commit and writes `historical` mode with that commit into the working tree. So the
  record that names the candidate is committed **after** the candidate, in a later freeze
  commit. The candidate cannot contain its own freeze.
- At the pinned commit, `specs/067-assurance-profiles/assurance.json` does **not** name
  `5bd9b5c7`. It still carries the previous freeze: both snapshots `historical` at
  `dad3e7f5`, and every `obtained_evidence` entry points at `evidence/t011.json` with the
  sha256 of that file at `dad3e7f5` (`c4754c82...`). A record that was never frozen would
  show `current` mode and a `null` commit. Either state is correct by design for a
  candidate. **Do not report it as a defect.**
- The binding to `5bd9b5c7` lives only in the later freeze commit (the merge of the
  re-freeze PR that adds this packet). That commit sets both snapshots to `historical` at
  `5bd9b5c7`, adds `docs/adr/0043-harness-mcp-readonly-surface.md` to the authority
  hashes, and rebinds all 10 `obtained_evidence` entries to `evidence/t011.json` at
  `5bd9b5c7`, sha256
  `86533edd5cd1561ef443ca4c29d1ad63c4a3b1ed929336ad64841adb0a92260a`.
