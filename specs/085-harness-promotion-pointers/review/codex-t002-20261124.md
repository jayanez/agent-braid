## What to check

1. **Regression acknowledgement (REQ-005, T001 record).** The T001 record adds a section
   "Regression acknowledgement (from the SPEC-083 T002 review)". It binds the move record
   to the SPEC-083 verdict hash and the regression summary hash, uses a graded summary
   (hard: baseline pass^n = 1 and candidate pass@n = 0; soft: a drop of at least 0.4), and
   relies on confirmation trials pre-registered in SPEC-083 (10 more per arm on up to five
   flagged tasks). Do the definitions in `spec.md` REQ-005, the T001 record and SPEC-083
   REQ-006 agree word for word in meaning (n versus 15 trials, which rate the 0.4 applies
   to, what "stands" after confirmation)? Is the hard-regression count the owner types
   fixed by the summary hash, so that a later summary cannot change what was acknowledged?
   Is the claim that "an agent cannot fill it in ahead" true for a script whose input an
   agent could pipe? Can private task titles reach the repository through the move record,
   the pull request, the script's own log or an error message?
2. **Freshness of the `candidate` gate.** The verdict must be bound to the current `adopted`
   hash (or SPEC-049 arm A while `adopted` is empty, OD-5) and the SPEC-082 corpus hash.
   What happens to an already-moved `candidate` when `adopted` changes or the corpus is
   refreshed? Is "stale" defined so that the same data cannot be both fresh and stale?
3. **Repository journal and concurrency (REQ-004, OD-2).** With the journal in the
   repository and every move landing through an owner-merged pull request, how do the
   extend-only save and `concurrent-update` refusal behave when two move pull requests are
   opened from the same base and both are squash-merged? Can a squash merge or a rebase
   produce a journal that replays without refusal but whose order no one reviewed?
4. **Owner-only moves (REQ-003, OD-3).** The actor is self-asserted and protection comes
   from OD-2. Is SC-003 testable as written ("a code search finds no caller that moves a
   label from an evaluation result")? Is the OD-3 condition (every interaction states when,
   where and the exact command; the script prints its precondition, directory and pull
   request) captured in a testable requirement and procedure?
5. **T013 interaction (REQ-006, REQ-007, REQ-008, OD-1, OD-6).** Check against
   `agent_braid/harness_promotion.py`: do T013 decisions carry per-axis `approved` records
   and a revocation that REQ-006 and REQ-007 can cite by hash? Does a T013 scope match the
   OD-6 "one pointer set per T013 registry scope"? Can `registry-status` in
   `agent_braid/harness_cli.py` take a pointer-journal argument and stay read-only? Is the
   divergence between `adopted` and the T013 active profile well defined when either is
   empty?
6. **Rollback (REQ-007, OD-4).** Rollback needs no new verdict when the target's evidence is
   not revoked. Can a rollback of `candidate` or `adopted` reach a hash whose verdict was
   bound to a different `adopted` or corpus hash, and is that intended?
7. **No authority (REQ-009).** Does any path let a label move begin a T013 transaction,
   change `AUTOMATIC_PROMOTION`, the SPEC-049 T008 `deferred` disposition or SPEC-050 D7, or
   reach the plugin `launch`, the SPEC-080 skill or an MCP tool?
8. **Traceability.** Do REQ, SC and procedure IDs match across `spec.md`, `assurance.json`,
   `tasks.md` and `validation-plan.md`? Are the dependencies between tasks acyclic?
