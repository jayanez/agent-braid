# Proposed verified-plan consumer contract v1 — DDP-T01

Status: local documentary candidate, not implemented or adopted. Subordinate to Constitution/Governance and existing native analysis/preparation versions. Use with the [decision contract](../../028-system-one-core/contracts/verified-plan-v1.md) and [conformance/migration](../../029-system-one-evaluation/verified-plan-conformance.md). All unknown keys/versions refuse. This is a new opt-in adapter boundary; do not add fields to native request v0.1.0-alpha, old DecisionResponse, existing tools or telemetry v1.

## Exact proposal (VPC-REQ-01)

`ConsumerProposal` has exactly these keys; ID/H/G/bounded JSON rules are those of the decision contract:

| Key | Type / rule |
|---|---|
| format | literal `s1-verified-consumer-proposal-v1` |
| consumerId | `core-api`, `mcp-service` or `mcp-stdio`, matching actual recipient |
| request | complete `s1-verified-request-v1` body |
| requestDigest | H = hash(request) |
| snapshot | complete AcquiredSnapshot body |
| snapshotDigest | H = snapshot.snapshotDigest, recomputed and independently reacquired |
| interpretationDigest | H = hash(request.interpretation), checked against observed IR |
| decision | complete VerifiedDecision body |
| decisionDigest | H = hash(decision) |
| verifierResult | complete VerifierResult body |
| runtimeRequest | null for semantic-defer; exact native request below for answered |
| executionAuthorization | false |
| proposalDigest | H = hash(all other proposal fields) |

No proposal is created for a refused decision. Refusal during proposal construction returns a local sanitized failure; it must not fabricate a valid packet. Bind the consumer ID even for defer. Recompute every body/digest, registry/verifier/policy pin, option-set/eligibility digest and ordered evidence reference. All three reference kinds require matching complete bodies, with interpretation body in request; omission or substitution refuses. New proposal limits are the complete raw/canonical 1MiB/depth16 limits, not a per-chunk loophole. A hash is not an authentication token. Do not accept a T022/T025 packet at this entry or a new packet at a legacy entry.

`runtimeRequest` is exactly `{gitRuntimeRequestVersion, repository, baseRevision, operations, order, expectedFinalTree}` with version `0.1.0-alpha`, original allowed local repository, acquired base commit, native operations, chosen plan sequence and nonzero G tree. Use the unchanged native request validator as an additional authority. Build operations through the existing native analysis mapping: retain instanceId/attemptId/dependencies and immutable commit source revisions; derive declaredWrites from the complete acquired paths in canonical path order. Each native operation has exactly {instanceId, attemptId, source, dependencies, uncertainPaths, declaredWrites}; source exactly {kind:"commit", revision:G}, uncertainPaths empty, declaredWrites the sorted acquired changed paths. In chosen serial order, dependencies are the sorted union of the original dependencies and all earlier instance IDs, matching native_request; operations array follows that order. Do not invent extra native operation fields. The existing adapter supplies its exact native operation form; before T06 integration, compare it with current `git_runtime._request` and `boundary_verification.observation.native_request`. New fields in this proposal never enter the native JSON request. The consumer must reconstruct the request from source, not deserialize a supplied ready-to-execute object blindly.

## Revalidation, tree construction and dispatch (VPC-REQ-02)

In order, within the shared outer budget:

1. Validate bounded JSON, exact format/recipient/authorization, all schema and pins; reject malformed data before source access. Check cancellation and remaining allowance.
2. Reacquire all immutable base/source objects from the same allowed repository, verify path/mode/source/dependency/goal/option/declaration bindings, rebuild complete program/snapshot and compare snapshot, IR and text digests. A source ref timestamp or matching producer hash is insufficient. Reject source/root drift, missing objects and incomplete observation. Source reads must not alter source index, refs, files, object store or configuration; materialize only owned scratch.
3. Rerun the complete finite verifier and bound registry/policy; selected answered ID must equal the policy's first eligible ID in this new envelope. T025 allowed any tied eligible choice; accepting that choice in a T025 packet does not establish new-policy selection. Semantic-defer must have no verified goal-reaching plan and no runtime request; return defer with zero native/consumer calls.
4. For answered, reconstruct the predicted **whole Git tree** from the exact pinned base in owned isolated scratch: start from base tree, apply T024 abstract line transitions to changed files, hash exact LF bytes as Git blobs, confirm each matches predicted blob IDs, update only those paths in a private index with mode100644, and write expected tree. Preserve unchanged base entries. Never derive the expected tree by replaying the source commits/patches or by T022's old EOF-blind builder. Compare full reconstructed native request and expected tree with proposal.
5. Invoke fresh native analysis/check through the unchanged bounded native verifier. Require verified native evidence, exactly one schedule, chosen order, complete status and final tree equal expected tree. Validate the full evidence/chunk protocol; a summary/digest without complete checked bodies refuses. Then invoke the existing native preparation consumer, which verifies again; do not remove repeated checks to meet a timing goal.
6. Check returned manifest.request equals the reconstructed request, last prepared step outputTree equals expected tree and complete evidence has valid bindings. Validate final cancellation/deadline before publishing answered. Hold scratch/admission until actual owned work stops; clean all owned scratch on positive, defer, refusal, timeout and cancellation paths. Record cleanup and termination failures even if the semantic outcome was earlier determined.

Fresh native check and prepare remain separate consumer calls; repeated acquisition, expected-tree construction and verification are separately counted. No cache/proof reuse is introduced. A future reuse scheme requires explicit freshness, invalidation, consumer/request scope and reviewed evidence completeness; it cannot skip native checks under this version.

## Exact delivery record and failure behavior (VPC-REQ-03)

`ConsumerResult` exactly `{format, consumerId, requestDigest, proposalDigest, decisionDigest, status, reasonCodes, preparedDigest, evidence, counters, usage, executionAuthorization}`. Format `s1-verified-consumer-result-v1`, status answered/semantic-defer/refused, false; pins H or null if unestablished on malformed input. preparedDigest is H=hash(complete native prepared body) only for answered, otherwise null. The complete body is returned through the existing bounded native evidence transport and validated before this digest is trusted; this wrapper neither expands frame/chunk limits nor implies that a large body fits one frame. `evidence` exactly `{nativeVerified: true|false|null, expectedFinalTree: G|null, observedFinalTree: G|null, preparedBodyChecked: true|false|null}`; null means not observed/unavailable, false means an observed failed check. Answered requires true, equal non-null trees and true body check. Semantic-defer requires all four null; refused may retain failed observations without asserting success. No prepared capability/grant/persistent run is returned.

`counters` exactly `{acquisitionCalls, verifierCalls, treeBuildCalls, nativeCalls, consumerCalls, executeCalls, recoverCalls, grantWrites, persistentRunAllocations}`; nonnegative integers or null if unmeasured. Last four must be measured zero on every accepted completion; unknown there prevents acceptance. Defer requires measured zero native/consumer/tree calls (pure verifier still runs); refusal-before-dispatch tests assert both zero. Actual cancellation may interrupt counters; unknown is not silently zero. `usage` is the exact local usage record in the decision contract, including every repeated phase. It is not a production telemetry event.

Consumer-only fixed reasons extend the decision taxonomy: `consumer-mismatch`, `proposal-digest-mismatch`, `inadmissible-choice`, `runtime-request-mismatch`, `target-tree-mismatch`, `native-not-verified`, `native-prepare-failed`, `transport-failure`, `evidence-incomplete`, `cleanup-failed`, `termination-unknown`. Inner sensitive exception text is sanitized; preserve detailed local diagnostic evidence separately. Never translate technical refusal into a negative semantic answer. Native observed disagreement refuses even if deterministic producer verification answered. Native preparation does not authorize execution.

Outer prepare budget starts at adapter ingress. All acquisition/decision/revalidation/tree/native/transport/cleanup phase caps come from the original request. Cross-process monotonic values are not portable: the parent enforces its own remaining outer budget, allocates a non-increasing child allowance, suppresses late responses and confirms termination/cleanup. Existing native functions cannot be promised to accept new deadline parameters they lack. A request with terminationMode other than cooperative returns exactly invalid-budget during request admission, before this consumer. Until T06 demonstrates enforceability, full-path deadline support stays pending. A cooperative timeout response is not proof that an underlying worker stopped. Existing cleanup/context-manager behavior is retained as observed evidence, not universal cancellation proof.

## Compatibility, rollout and rollback (VPC-REQ-04)

Core API, ToolingService and actual stdio are three distinct tested consumers, not one mocked route. This contract initially describes internal library adapters and local test harnesses only. Existing native/public method names and registered tool lists stay unchanged. T06 may reuse the existing read-only preparation surface, with explicit validated mappings, but adding a public advice endpoint, schema/registry entry or default behavior needs its own governance review and assignment. Feature off preserves exact legacy output/error behavior and does not import optional ML packages. No training, calibration, source collection, persistent run, execution/recovery, grant write, admission/promotion or activation is authorized by any of these fields.

Rollback disables the new opt-in composition path; it does not revert research evidence or mutate historical assurance. Coordinator freezes a candidate-local allowlisted registry and actual extracted-source digests before integration tests. Unknown/pending digest entries are unavailable, not wildcards. Source drift from T025's research candidate to current public develop must be checked at actual consumer integration; the intervening SPEC-047 telemetry merge is not assumed equivalent merely because it is default-off.

The initial internal composition accepts proposals only within the active coordinator-owned request context that began before acquisition/selection. Consumer reacquisition receives that same trusted context and aggregate Git budget; reparsing wire budgets cannot establish a new start or reset spent counters. Stdio children remain under the live parent context/remaining allowance. Standalone persisted/external proposal reuse without that active binding is unsupported and refuses; defining a future separate ingress/episode is a distinct reviewed contract. No timestamp/hash in the proposal can manufacture the local context.
