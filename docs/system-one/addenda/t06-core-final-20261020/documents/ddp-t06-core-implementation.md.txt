`CoreRequestContext` exposes `propose`, `consume`, `prepared` and the trusted local context; `prepare_core` is a Python convenience returning the exact result and complete prepared body or None. Contexts are request-local and nonserializable. Persisted/external proposals cannot recreate the original binding. Old producer snapshots remain immutable; complete proposal evidence retains the exact producer body and digest used in that proposal.

Three existing modules change with explicit before/after hashes in the packet. `git_replay` and `git_runtime.prepare_run` gain optional trusted Python budget seams and place scratch under that same budget root; default behavior is retained. `system_one_verified_selection` gains a default-preserving trusted budget factory, read-only actual work counts and downstream `seal(factory)` under the existing token publication lock. No callable or budget factory is admitted from wire input. The consumer budget subclass tightens each native phase's original local caps as well as the outer request allowance, without resetting counters/start/deadline. Native preparation retains its 60-second/256-command/8-MiB aggregate/2-MiB per-command ceilings; larger outer allowances cannot relax them. Limits are cooperative, with sampled scratch and cleanup reporting, not a universal hard wall SLA.

## Source-bound software capture and latency

Final serial capture on the M3 Pro used the existing isolated Python 3.12 environment: 21 tests, zero failures/errors/skips, 81.578 seconds. Its source archive has seven verified members (six registered inputs plus capture helper), and source inputs remained identical. The 22 tagged related fixture controls returned eight expected answers with complete prepared-body digest matches, two correct semantic deferrals and twelve expected technical refusals of forged proposals. Accepted errors: 0/8. Matched EN/ES status/reason consistency: 11/11 pairs. These are related synthetic software fixtures, not independent accuracy observations, general NLP evaluation, a representative workload, confirmatory holdout or Laya parity. The mixed 8/22 answered fraction includes deliberately forged inputs and is not a workload coverage target or a <=1% error screening result.

For eight positive controls, descriptive medians were: pure decision 3.560 ms, aggregate acquisition 676.070 ms, native check 1,801.433 ms, native preparation 967.578 ms, entry through cleanup 3,949.410 ms, and externally measured entry through returned result 3,950.138 ms (range 3,127.951–5,968.031 ms). `prepareNs` covers the full entry-through-cleanup interval, including producer work. Stage spans are nested and must not be summed. Acquisition and native checks dominate these fixtures; optimizing by removing freshness or independent native checks is not justified. There is no before/after performance improvement claim or universal latency guarantee.
