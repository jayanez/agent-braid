## Findings

**P2 — `seal(factory)` releases token ownership after a factory exception while leaving the context retryable** — `agent_braid/system_one_verified_selection.py:504-521`; Core call at `agent_braid/system_one_verified_consumers.py:330`.

If the trusted downstream factory raises after cleanup, `_published` remains false, then the `finally` block removes the waker and releases the cancellation token. A subsequent `seal()` takes `_publish()` again with `_claimed == False`, so line 515 calls `final(False)` directly without `CancellationToken.publish()`'s lock. A different request can claim that token in the meantime, yet the old context can still run its factory and publish an `answered` result.

I confirmed this with a small deterministic software check: a valid producer context called `seal()` with a factory that raises, then another owner claimed the token; a second `seal()` on the old context invoked the factory and returned `answered` while the other owner still held the token. The token publication wrapper was called once total, on the failed first attempt. This directly violates the atomic ownership/publication boundary if result construction fails.

Minimal fix: make a factory exception terminal for the context before releasing ownership. Preserve a sanitized failure/refused state and prevent any later factory invocation from using the unclaimed fast path; add a regression that raises once, lets a second request claim the token, and verifies the old context cannot publish or invoke its factory again.

**P2 — known consumer failures are also reported as `internal-failure`** — `agent_braid/system_one_verified_consumers.py:325-327` and `:279-307`.

The consumer exception mapper recognizes the consumer-specific taxonomy, but the catch passes only producer `_REASONS` through to `VerifiedRequestContext._fail`; known consumer reasons become producer `internal-failure`. `_record()` then unions that producer reason with the original consumer reason. A valid proposal changed to `consumerId: mcp-service` with its proposal digest recomputed returns `status=refused`, `reasonCodes=('consumer-mismatch', 'internal-failure')`, and zero native calls. `internal-failure` is inaccurate for this deliberate recipient mismatch and muddies the contract's sanitized diagnostic taxonomy.

Minimal fix: keep the producer's internal failure mapping where required, but construct ConsumerResult reason codes from the original known consumer reason without adding `internal-failure` for that same handled refusal. Assert the exact reason tuple for consumer mismatch and the other consumer-only reasons.

**P2 — revalidation counters increment before either underlying operation begins** — `agent_braid/system_one_verified_consumers.py:313-316`.

After proposal admission, the code increments both `acquisitionCalls` and `verifierCalls` before `revalidate()`. If cancellation arrives after proposal creation but before consume, `revalidate()` refuses at `handoffRevalidation` entry before source reacquisition or verifier invocation, yet the result reports 2 acquisition calls and 2 verifier calls (the only actual acquisition/verifier work was the producer's initial call). The contract requires counters to describe observed calls and says interrupted work may be unknown rather than silently reported as executed.

A small deterministic cancellation-before-consume check returned exactly that result: refused/cancelled, acquisitionCalls 2, verifierCalls 2. Minimal fix: increment each counter at the corresponding actual acquisition/verifier invocation boundary, or report null/otherwise distinguish an unentered attempt when cancellation prevents those operations. Add a cancellation-at-revalidation-entry assertion.
