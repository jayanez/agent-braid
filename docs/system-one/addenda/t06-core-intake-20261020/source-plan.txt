## Interfaces and justified source changes

New files: `agent_braid/system_one_verified_consumers.py` and `tests/test_system_one_verified_consumers.py`. No default tool/catalog changes or learned dependencies.

The actual native Core APIs otherwise create new Git budgets and scratch roots. Add optional trusted Python `budget` keywords to `git_replay.produce`, `git_replay.verify`, its internal evidence builder and `git_runtime.prepare_run`; defaults retain existing behavior and wire schemas. Supplied budgets are the identical original request object, reused across independent native replay and preparation; temporary native work lives under its scratch root. Do not change the frozen M2 process runner or reset limits/counters/start time.

T05 gains a trusted `budget_factory` constructor seam, defaulting to the existing GitCommandBudget. The new adapter supplies a subclass that checks the live phase and limits each Git command timeout to remaining stage time before delegating to the same aggregate counter. No global patch, observer mutation or wire callable is used. Native phases additionally retain their original per-invocation wall/command/output ceilings (including preparation 60 seconds, 256 commands, 8 MiB aggregate and 2 MiB per-command output); a larger outer request cannot relax them. Producer acquisition and verifier invocation counts are observed at their actual function boundaries, excluding cancellation before entry. Failed downstream result factories terminally seal refusal before releasing the token, so another request claiming the token cannot enable an old-context retry. T05 also gains `seal(factory)` to construct the downstream immutable result under the same cancellation publication lock before release, with a cancellation/deadline recheck after bounded serialization. Ordinary producer `publish` stays idempotent. Existing T05 tests must remain green.

`CoreRequestContext.propose` retains the exact immutable producer body and complete evidence. `consume(raw)` admits bounded raw JSON and checks exact bodies/digests against that live proposal before source access, then freshly reacquires/reverifies, reconstructs the whole expected tree from base plus abstract line effects, calls real native replay/independent verification and preparation, validates complete returned bodies and seals the exact ConsumerResult. `prepared` exposes the full checked native body separately. `prepare_core` returns a Python tuple of ConsumerResult and complete prepared body or None, with owned cleanup; it does not invent a wire wrapper. Persisted/external proposals without the active producer binding refuse.

## Capture and performance interpretation

Before the stable capture, bind code/tests/protocol, previous-file inventory, environment and command. Retain prior development logs and every subsequent attempt. Run serially with existing isolated Python 3.12 and local Git, no downloads/services/paid CI. Capture complete ConsumerResult records for the identified EN/ES scenario matrix and keep other negative-test outcomes in their full unittest log. These are software conformance receipts, not training examples or a new scientific decision-accuracy estimate.

Report status, expected outcome and counter mismatches by named family. Do not let always-defer count as success: positive fixtures must prepare, true no-option cases must defer with zero tree/native/preparation calls, malformed/drift cases must refuse before dispatch. Report EN/ES pair consistency on matched controls; translations and related views are not independent observations.

Report actual acquisition, decision, expected-tree, handoff, native-check, native-prepare, cleanup and entry-to-cleanup spans separately. Complete `prepareNs` includes producer acquisition/decision and cleanup; nested stage spans are not added to that total. Test requests use prepare cap 120,000 ms, acquisition cap 60,000 ms, decision cap 30,000 ms, individual stage caps 30,000 ms and cleanup opportunity 1,000 ms, with 512 aggregate Git commands, 128 hunk applications, 16 MiB aggregate output and 64 MiB sampled scratch. These are observed fixture allowances, not universal latency support or a hard wall SLA. Small-sample latency summaries are descriptive only. Do not remove repeated native/source checks or introduce caches to make timing look better.

Any accepted malformed/stale choice, missing full evidence, tree disagreement or late success blocks closure of this increment. Preserve the counterexample and correct only the implicated scope. Perform bounded technical review with concrete findings, focused affected checks, proportional quick and one PR profile on the stable candidate. Profiles, source-bound software capture, human review and scientific acceptance are separate. No automatic retry after a failed capture; diagnose and retain it before a deliberate new attempt.
