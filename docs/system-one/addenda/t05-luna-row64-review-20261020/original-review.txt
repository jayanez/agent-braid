## Finding

**P2 — checkpoint row-cap rejection does not latch refusal in the live context** — [`agent_braid/system_one_verified_selection.py:228`](/Users/juanyanez/Documents/Codex/2026-10-20/agent-braid-verified-core/agent_braid/system_one_verified_selection.py:228), especially lines 230–231 and 283–288.

`_check()` latches cancellation/deadline failures, and `phase()` catches and latches failures. But when `checkpoint()` needs a new automatic stage row, `_open()` enforces `len(_rows) < 64` with a bare `_require` outside `_check()`'s catch. A trusted caller can catch that `ValueError`; `_failure` remains unset, the context's decision remains `answered`, and its complete evidence remains available after the reported work-budget failure. The request can therefore continue exposing a stale successful producer result until cleanup. This violates the contract's irreversible cancellation/deadline/work-budget refusal behavior and fails closed only later.

Reproduced through the public context API with the existing owned software fixture: decide to `answered`, add valid selection phase rows until 63, open row 64 with `checkpoint('selection', 0)`, then catch `checkpoint('verification', 0)` raising `work-budget-exceeded`. Immediately afterward, observed `_failure is None`, `context.decision['status'] == 'answered'`, and nonempty evidence. `publish()` did refuse with `work-budget-exceeded`, because `close()` cannot append the cleanup row at 64; **there is no final publication bypass in this reproduction**. The defect is the stale live producer state before close, despite a caught budget error.

Minimal fix: make the row-cap failure in `_open()` call `_fail('work-budget-exceeded')` before raising, and reserve a cleanup row by limiting operational rows to 63. Add a regression that catches the automatic checkpoint failure and asserts immediate refusal plus cleared semantic bodies, then verifies cleanup still records its row and publication remains refused.
